# Pellet firmware v2.3.0

Release date: 2026-09-23

Source tag: `v2.3.0`<br>
Source commit: `dc41a67` (the implementation), merged to `main` as
`2704870`. The tag itself sits on the commit that adds these notes, which
cannot name its own hash.

## Changes

- Implement `JERRYCAN_CMD_CAPABILITIES_REQUEST` (`0x23`) and
  `JERRYCAN_CMD_CAPABILITIES_RESPONSE` (`0x24`), the capability query the host
  has been sending since before any firmware answered it. Every release
  through v2.2.0 dropped the frame silently, so reachAQ had to infer a board's
  abilities from its version string against a hand-maintained table.
- Report a capability bitmask whose bits are the host's own, a wire schema
  version, and a boot id drawn once per start.
- Derive the finite-pulse bit from `DT_HAS_CHOSEN(ll_gpio_pulse_counter)`, the
  same condition `gpio.c` uses to decide whether it can serve a pulse at all,
  so a board cannot advertise a pulse it would refuse.
- Enable `CONFIG_ENTROPY_GENERATOR` so the boot id has a hardware source. The
  board's `rng` node was already `okay`; only the driver behind it was missing.

## Wire protocol

`JERRYCAN_CMD_CAPABILITIES_REQUEST = 0x23`, host to board, 1 byte:

| Field | Type | Meaning |
| --- | --- | --- |
| `rsvd` | `uint8` | Reserved, send zero |

`JERRYCAN_CMD_CAPABILITIES_RESPONSE = 0x24`, board to host, 9 bytes:

| Field | Type | Meaning |
| --- | --- | --- |
| `wire_schema_version` | `uint8` | Frame layout generation; `1` for this release |
| `capabilities` | `uint32` | Bitmask, little endian |
| `boot_id` | `uint32` | Changes on every board start |

## Capability bits

| Bit | Name | Set by this firmware |
| --- | --- | --- |
| `1 << 0` | `TIMING_TRAILER` | No |
| `1 << 1` | `TIME_SYNC` | No |
| `1 << 2` | `FINITE_GPIO_PULSE` | Yes, where the board has a pulse counter |
| `1 << 3` | `PELLET_PRECHECK` | No |

Two are deliberately never set. `TIMING_TRAILER` because nothing in this
firmware appends one and nothing in the host reads one; it is a reserved name
on both sides. `TIME_SYNC` because `TIME_SYNC_REQUEST` (`0x1F`) has no handler
here and no entry in the command enum, so a board claiming it would be asked
for a sync it cannot perform.

A bit is set only where the feature is genuinely present. Advertising an
absent capability is worse than the silence it replaces, because the host
stops guarding against what a board claims to have.

## Boot id

Drawn once at init and constant for the life of that boot, so a value that
changes means the board restarted and nothing else. This matters because a
reboot silently discards configuration the host believes it has written, and
until now the host had no way to notice.

## Limits

- Capability reporting says what a board can do, not whether it is wired
  correctly. `FINITE_GPIO_PULSE` means the board will serve a pulse, not that
  anything is connected to the pin.
- The bitmask is per board, not per line. A board reports that it can pulse;
  which lines it will pulse is still the `pulse-enable-gpio-names` property
  and is still refused per line with `-EPERM`.

## Behavior changes

None outside the new frames. v2.2.0 behavior is unchanged: the finite pulse
still works on `STIM2` and `STIM3`, a pulse addressed to a tone confirmation
line is still refused with `-EPERM`, and 5 kHz Tone 1 still drives only
`STIM0` while 6 kHz Tone 2 drives only `STIM1`.

## Acceptance criteria

- Firmware version request reports `2.3.0` after reboot and finalization.
- A `CAPABILITIES_REQUEST` (`0x460` to board address 0) draws a
  `CAPABILITIES_RESPONSE` on `0x480`.
- That response carries `wire_schema_version = 1` and
  `capabilities = 0x00000004` on a board with a pulse counter.
- The `boot_id` is non-zero and identical across repeated requests within one
  boot.
- The `boot_id` differs after a board reboot, with the other two fields
  unchanged.
- v2.2.0 behavior is unchanged: a 500 ms pulse on `gpio_idx` 7 still raises
  and clears `STIM3`, and a pulse on `gpio_idx` 4 or 5 is still refused with
  `-EPERM`.
- 5 kHz raises `STIM0` only, 6 kHz raises `STIM1` only, and any other
  frequency raises neither.

## How to verify on a rig

```bash
candump -T 30000 'can0,480:7FF' > /tmp/caps.log &
# ask the board for its capabilities, then reboot it and ask again
```

The request frame is arbitration id `0x460` and the response is `0x480`; the
arbitration id is `command_type << 5`. Each response is nine payload bytes
read little endian as `<BII`:

```text
01 04 00 00 00 11 2F 92 9C
^^ wire_schema_version = 1
   ^^^^^^^^^^^ capabilities = 0x00000004
               ^^^^^^^^^^^ boot_id
```

Reboot the board between two captures and check that only the last four bytes
change.

## Deployment record

`christielab10`, pellet board at address 0, 2026-09-23. Flashed twice so both
MCUboot slots carry the release; a revert now lands on 2.3.0 rather than
2.2.0.

Observed on the bus, board address 0, before the tagged release was built:

- `0x460` drew no response at all on 2.2.0, reproducing the silence this
  release fixes.
- After the change, `0x480` carried `01 04 00 00 00 11 2F 92 9C` three times
  running.
- Across a `board_reboot`, the boot id moved from `0x9C922F11` to
  `0x4571A5D7` with the other fields unchanged.
- The pulse and tone behavior of v2.2.0 was re-checked and unchanged.

## Host work now possible

With a firmware that answers the request, reachAQ can move
`finite_stim3_pulse` from `optional_capabilities` to `required_capabilities`
for this version in `config/pellet-firmware-compatibility.yaml`. That was
deliberately left optional for v2.1.0 and v2.2.0 because requiring it would
have rejected every real board, which is the trap those entries record.
