# Pellet firmware v2.2.0

Release date: 2026-09-17

Source tag: `v2.2.0`<br>
Source commit: _filled in below once the release is built_

## Changes

- Implement `JERRYCAN_CMD_GPIO_PULSE` (`0x21`), the finite, firmware-timed
  digital pulse the host has been sending since before any firmware answered
  it. All releases through v2.1.0 dropped the frame silently.
- Add `JERRYCAN_CMD_GPIO_PULSE_STATUS` (`0x22`), the board-to-host report for
  that pulse.
- Time both edges from TIM16 as a Zephyr counter rather than from the kernel
  tick, so the pulse width does not depend on the scheduler.
- Add the `pulse-enable-gpio-names` property to `ll,generic-gpios` and the
  `ll,gpio-pulse-counter` chosen node, so a board opts a line in explicitly.

## Wire protocol

Both payloads are little-endian and packed. The transport appends the uuid byte
after the payload, as for every other command.

`JERRYCAN_CMD_GPIO_PULSE = 0x21`, host to board, 7 bytes:

| Field | Type | Notes |
| --- | --- | --- |
| `instance` | `uint8` | generic-gpio instance, `0` on the pellet board |
| `gpio_idx` | `uint16` | readable-pin index: `6` = STIM2, `7` = STIM3 |
| `duration_us` | `uint32` | 100 us through 5 s |

`JERRYCAN_CMD_GPIO_PULSE_STATUS = 0x22`, board to host, 12 bytes:

| Field | Type | Notes |
| --- | --- | --- |
| `instance` | `uint8` | echoed |
| `gpio_idx` | `uint16` | echoed |
| `duration_us` | `uint32` | echoed, the duration actually applied |
| `phase` | `uint8` | `0` rejected, `1` asserted, `2` completed |
| `error` | `int32` | zero on success, negative errno otherwise |

The board emits `phase = 1` when the line goes high and `phase = 2` when it
returns low. A refused command emits `phase = 0` carrying the same errno that
the ordinary `JERRYCAN_RSP_ACK` carries, so a rejection is both acknowledged and
reported.

`software/libjerrycan` gained the matching size-map entries and pybind
bindings (`GPIOPulse`, `GPIOPulseStatus`), so a host using `pyjerrycan` can
decode the status message.

## Pin mapping

Host stimulus names are off by one from the board's silkscreen names.

| Board name | MCU pin | `gpio_idx` on the wire | Host `DigitalOutputs` | Pulse capable |
| --- | --- | --- | --- | --- |
| STIM0 | `gpiob 11` | 4 | `STIMULUS_1` | no |
| STIM1 | `gpiob 12` | 5 | `STIMULUS_2` | no |
| STIM2 | `gpiob 13` | 6 | `STIMULUS_3` | yes |
| STIM3 | `gpiob 14` | 7 | `STIMULUS_4` | yes |

STIM0 and STIM1 are the tone generator's Tone 1 (5 kHz) and Tone 2 (6 kHz) TTL
confirmations, declared in the DTS as `tone-output-gpios`. A pulse would contend
with tone confirmation, so a pulse addressed to `gpio_idx` 4 or 5 is refused with
`-EPERM` rather than driven.

## Timing

TIM16 is the only free timer on this board with a capture/compare channel, so it
is the one that can act as a Zephyr counter. It runs at 1 MHz, giving 1 us
resolution, and it is 16-bit, so a single alarm spans at most 65.535 ms. Pulses
longer than half the counter range are served by chaining alarms, charging each
hop by the compare value it fired on so the total length does not drift as hops
accumulate.

Rejected alternatives: TIM6 and TIM7 are free but are basic timers with no
capture/compare channel, so Zephyr's STM32 counter driver cannot raise an alarm
on them. Every other timer on this board is already committed to a stepper, a
servo, an LED PWM channel, or the tone generator's sample clock.

A `k_work_delayable` failsafe is armed before the line moves and cancelled when
the counter path completes. If the counter path ever fails, the failsafe forces
the line low 20 ms past the requested duration and reports `phase = 2` with
`error = -ETIME`. A stimulus line left asserted is worse than a pulse of the
wrong length.

**Edge accuracy has not been measured.** The CAN-capture acceptance check below
confirms the pulse happens and is about the right length; it cannot resolve the
short end of the range. Put a scope on the BNC and measure a 100 us and a 1 ms
pulse before trusting this path for optogenetics timing, and record the measured
width and jitter here.

## Limits

- One pulse is in flight at a time, board-wide: the counter has a single alarm
  channel. A second pulse arriving while one is running is refused with
  `-EBUSY` rather than extending or restarting the first.
- A duration outside 100 us through 5 s is refused with `-EINVAL`.
- A board that declares no `ll,gpio-pulse-counter` refuses every pulse with
  `-ENOTSUP`. The magnet board is unchanged and still has no pulse command, but
  it now reports that fact instead of ignoring the frame.

## Behavior changes

- Nothing else changes. v2.1.0 pressure streams, v2.0.0 tone-to-stimulus
  behavior, `GPIO_READ`, and `GPIO_WRITE` are untouched.
- `GPIO_READ` is now also transmitted immediately on both pulse edges, in
  addition to its periodic 100 ms report.

## Acceptance criteria

- Firmware version request reports `2.2.0` after reboot and finalization.
- A 500 ms pulse on `gpio_idx` 7 raises bit 7 in `GPIO_READ` (`0x140`) for about
  500 ms and it returns low on its own.
- A 500 ms pulse on `gpio_idx` 6 does the same for bit 6.
- `GPIO_PULSE_STATUS` (`0x440`) arrives twice per accepted pulse, `phase = 1`
  then `phase = 2`, both with `error = 0`.
- A pulse on `gpio_idx` 7 with `duration_us` below 100 or above 5000000 is
  refused with `phase = 0`, `error = -22` (`-EINVAL`), and the line never rises.
- A pulse on `gpio_idx` 4 or 5 is refused with `phase = 0`, `error = -1`
  (`-EPERM`), and neither tone confirmation line moves.
- v2.1.0 behavior is unchanged: both pressure streams still arrive, and 5 kHz
  Tone 1 still drives only `STIM0` while 6 kHz Tone 2 drives only `STIM1`.

## How to verify on a rig

```bash
candump -tz can0 > /tmp/can_capture.log &
# send a 500 ms pulse on STIM3 (gpio_idx 7), then on STIM2 (gpio_idx 6)
```

The pulse frame is arbitration id `0x420` and the status frame is `0x440`; the
arbitration id is `command_type << 5`. Check that `GPIO_READ` (`0x140`) reports
the corresponding bit set for about 500 ms after each pulse frame and returns
low without a second command.

The physical BNC-to-STIM mapping is still unconfirmed. The board carries six
BNCs (J11, J15-J18, J21) and the schematic has not been traced, so confirm which
connector carries STIM2 and STIM3 before wiring anything to them.

## Host work still outstanding

This release ships the board side only. The host still needs, in
`Cerebellum-Lab/reachAQ`:

1. `pulse_digital_output` widened from `STIMULUS_4` to `STIMULUS_3` and
   `STIMULUS_4`, in both `can_interface.py` and `emulation_interface.py`.
2. `firmware_compatibility.py` and `config/pellet-firmware-compatibility.yaml`
   taught about 2.2.0 and the `finite_stim3_pulse` capability bit.
3. Line selection on `LaserPulseProfile` and on the bench stim test.
4. `pulse_digital_output` waiting for `GPIO_PULSE_STATUS` and failing when it
   does not arrive, so a board without the command stops looking successful.

Capability reporting (`CAPABILITIES_REQUEST = 0x23` and
`CAPABILITIES_RESPONSE = 0x24`) is still unimplemented on the board. The host
tolerates a board that reports nothing, so the pulse ships without it.
