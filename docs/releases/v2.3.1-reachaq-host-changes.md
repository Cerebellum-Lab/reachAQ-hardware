# Pellet firmware v2.3.1: what reachAQ (the host) must change

This is a hand-off note. Nothing in reachAQ was changed to write it.

The v2.3.1 pellet firmware refuses or interrupts motion and says so in the
`error` field of its ACK. Today's reachAQ throws that field away at the first
step of the command loop, so a refused move looks the same as a finished one.
Below is where, and what has to change.

**Basis**

- Firmware: this worktree at `28cb687`: `docs/releases/v2.3.1.md`,
  `software/libjerrycan/inc/jerrycan_types.h`,
  `firmware/lib/jerrycan/modules/{stepper,servo,tone}.c`,
  `firmware/lib/jerrycan/jerrycan.c`,
  `firmware/lib/motor_motion/{stepper_power_policy.c,motor_motion_workq.c}`.
  v2.3.1 is untagged and has not run on a board, so every statement about the
  board here is from code.
- reachAQ: branch `devel` at `7144a03f`. The brief named `90f7c6b7`; `devel` has
  moved since. Of the files used here only `can_device.py` differs between the
  two (88 lines: the stimulus-pulse "lost ack" path). `_handle_ack` was at
  `can_device.py:982-993` on `90f7c6b7` and is at `1052-1063` now. **Every
  `file:line` below is for `7144a03f`.** Paths are relative to the reachAQ root.

**Evidence tags**: **(V)** read in the code at the cited line. **(I)** follows
from the code but was not run. **(U)** could not be checked from here.

## How an ACK travels today

1. Firmware sends `RSP_ACK` (`0x30`): int32 `error`, then the uuid byte
   (`jerrycan.c:203-214`; refusals are sent at once at `jerrycan.c:187-190`) (V).
2. `auto-trainer-device/src/autotrainer/device/socketcan_jerrycan.py:754-755`
   decodes `message.ack.error = struct.unpack("<i", payload)[0]` (signed) (V).
   The other transport, `pyjerrycan`, is an external compiled module (U).
3. `can_interface.py:466-470` builds `Acknowledge(uuid, error)`. The error is
   kept since commit `f627d599` (V). `Acknowledge.is_failure` and
   `failure_reason` (`device_interface.py:473-481`) have no caller outside
   `tests/acknowledge_error_test.py` (V).
4. `device_connection.py:399-402` reads frames and calls
   `CanDevice.notify_data` (`can_device.py:1415-1432`). `_data_handlers[Acknowledge]`
   is `_handle_ack` (`:566`). **`_handle_ack` (`:1052-1063`) queues
   `(_uuid_ack, (msg.uuid, perf_c), None)`. The error is dropped here** (V).
5. The command loop (`:635-997`) matches the uuid at `:696-721`, clears the
   pending state, and inserts `(_uuid_ack, data, ctx)` at `:702`. It then sends
   the next compound step (`:815-897`) or, with no steps left, calls
   `_acknowledge_command(ctx)` at `:995`. Nothing looks at an error (V).
6. `Device._acknowledge_command` (`device.py:66-71`) posts API event
   `deviceCommandAcknowledge` and `api.send_message(ACKNOWLEDGE, (token, perf_c))` (V).
7. `MessageHandler` (`auto-trainer-core/.../message_handler.py:106-131`) calls
   `decoded_message_received` (HardwareModel `_decoded_device_message`
   `hardware_model.py:1005`; session recorder `_on_device_message`) and
   `ack_received(tok, perf_c=...)` (V).
8. `ack_received` subscribers:
   - `HardwareModel._ack_received` (`hardware_model.py:1430-1441`): pops the
     pending token, outcome "acknowledged".
   - `PelletMachine._pellet_device_ack_received`
     (`auto-trainer-behavior/.../pellet_machine.py:387-450`): `pellet_sent`,
     `pellet_released`, home and retract events.
   - `tools/pellet_delivery/model/app_model.py:392-396`.
   - `DeviceConnection.await_acknowledge` (`device_connection.py:196-222`),
     used by connect (`hardware_model.py:665-691`) and the motor-config write
     (`device_connection.py:242-266`).
9. `AppModel._on_pellet_sent` (`tools/acquisition/model/app_model.py:12050-12092`)
   counts the pellet as presented (V).

Retries happen only on an ACK **timeout**: default 3 s
(`can_device.py:171`), `default_command_ack_timeout_repeat_count = 3`
(`:173`). The third timeout raises (`:766-777`), so a command is sent once and
resent twice. Relative moves refuse a resend (`:781-792`). The raise ends the
command thread through `_command_handler` (`:610-633`) as a terminal
`CanFailure(ACKNOWLEDGEMENT_TIMEOUT)` (V). A per-motor `uuid_ack_timeout` from
`~/Autotrainer/motor_config.yaml` can lengthen it (`:380-381`, `:1847-1854`);
the rig's values are (U).

## What the board sends (checked against the firmware)

- Every motion command (`STEPPER_MOVE`, `STEPPER_HOME`, `FIXED_XYZ`,
  `SERVO_MOVE`) gets one ACK with `error`. A refusal is ACKed at once. A move
  that was running when it was stopped is ACKed on the next 100 ms status tick
  with the board-wide error at that moment (`stepper.c:177-194`) (V).
- `-EPERM` (-1): ESTOP asserted (`stepper_power_policy.c:58-60`,
  `motor_motion_workq.c:603-605` for servos). `-EIO` (-5): driver fault latched
  or drivers not proven (`:64-66`). `-ETIMEDOUT` (-116): host silent (`:67-69`).
  `-EBUSY` (-16): axis moving (`motor_motion_workq.c:747-750`) **or** axis needs
  homing (`:752-755`) (V). `stepper_home` returns `-EPERM`/`-EIO`/`-ETIMEDOUT`
  from `stepper_power_recover()` (`:849-852`) and `-EBUSY` if moving (`:861-864`) (V).
- `-EAGAIN` (-11): the move is within a threshold of the current position
  (`motor_motion_workq.c:758-761`). **The threshold is `1/microsteps` turn, not a
  fixed 0.125 turn.** It is 0.125 turn only at `microsteps = 8`. reachAQ's
  default `StepperConfig.microsteps` is 64 (`device_interface.py:286`), which is
  1/64 turn, about 0.04 mm at `_MM_PER_TURN = 48/19.7` (`stepper_motor.py:6`).
  The rig's value is in `motor_config.yaml` (U). It does not change what the host
  should do: any `-EAGAIN` is success. `-EAGAIN` is checked **after** the
  "needs homing" `-EBUSY` (V).
- `FIXED_XYZ` visits X, Z, Y and reports the first axis refused
  (`stepper.c:144-167`, `:196-243`). **A refused axis does not stop the others:
  `attempt_motor_move` returns false and the sequence moves on to the next axis**
  (V). After a `FIXED_XYZ` refusal the stage can be at a mixed pose.
- Error numbers are picolibc's. `-116` is `ETIMEDOUT` here and 110 on Linux
  (`errno.ETIMEDOUT` on the host is 110, or 10060 on Windows). Compare against
  literals (release note; V).
- `STEPPER_STATUS.status`: bit 0 driver fault, bit 1 enable off
  (`jerrycan_types.h:360-373`, `stepper_power_policy.c:90-111`). The socketcan
  decoder already reads the byte (`socketcan_jerrycan.py:308-315`, `:748-750`) (V).
- Capability bit 6 is `JERRYCAN_CAPABILITY_STEPPER_DRIVER_FAULT`
  (`jerrycan_types.h:276`) (V).
- ESTOP: `stepper.c:359-364`, payload non-zero asserts, zero releases, no ACK (V).
- `-EPERM` and `-EBUSY` also mean other things for `GPIO_PULSE`: `-EPERM` for a
  pulse aimed at a line that is not a stimulus output, `-EBUSY` for a pulse
  already in flight (`config/pellet-firmware-compatibility.yaml:47`;
  `device_interface.py:465-470`; V from the host's own notes, the firmware
  handler `gpio.c` not read in full). **A code means nothing until the command
  class is known** (R5).

# Required before deploying v1.3 boards

## R1. Allowlist entry and capability bit

- **Today**: the newest entry in `config/pellet-firmware-compatibility.yaml` is
  2.3.0 (`:4-51`). An unlisted version gives `supported=False`
  (`tools/acquisition/model/firmware_compatibility.py:90-99`) and
  `HardwareModel.connect` raises (`hardware_model.py:699-704`) (V).
- **Must do**: add a `2.3.1` entry modelled on 2.3.0: `wire_schema_version: 1`,
  `required_capabilities: [finite_stim3_pulse]` (both boards report bit 2:
  v1.2 `0x04`, v1.3 `0x44`), `optional_capabilities: [timing_trailer,
  time_sync, stepper_driver_fault]`, `hardware_release: v2.3.1`,
  `qualification_status: rollout_pending`, `qualification_date: null`. Its
  `limitations` should say it has not run on a board. Add
  `"stepper_driver_fault": 1 << 6` to `CAPABILITY_BITS` (`:13-21`).
- **Order matters**: `FirmwareCompatibilityPolicy.load` raises
  `ValueError("Unknown firmware capability in policy")` for any name missing
  from `CAPABILITY_BITS` (`:68-73`). Land the bit before, or in the same commit
  as, the YAML entry. Otherwise **every** version is rejected, not just 2.3.1 (V).
- **Required or optional: optional.** A v1.2 board on 2.3.1 reports `0x04`
  without bit 6 and is supported. A required bit would reject it, because
  `commands_allowed` is `supported and not missing_capabilities`
  (`:40-41`, `:111-112`) (V). The policy has no hardware-revision field, so it
  cannot express "required on v1.3 only" (V).
- **Gap this leaves (I)**: a v1.3 board that reports no bit 6 (running 2.3.0 or
  older, or a PD2 sample that read low) is indistinguishable from a v1.2 board.
  It accepts moves and does not move. The host cannot tell from capabilities;
  a home that never reaches its switch is the only symptom. See S4.

## R2. Carry `error` from `_handle_ack` into the command loop

- **Today**: `_handle_ack` (`can_device.py:1052-1063`) has `msg.error` but queues
  `(msg.uuid, perf_c)`. The loop unpacks two values at `:697`.
- **Must do**: queue `(msg.uuid, perf_c, int(msg.error))`; unpack three at
  `:697`; keep `cur_commands.insert(0, (_uuid_ack, data, ...))` (`:702`) working
  with the wider tuple, and fix any other place that builds a `_uuid_ack` entry
  (tests do: `can_device_test.py:739-744` calls `_handle_ack`; none builds the
  tuple directly (V)).
- **Why**: everything downstream (R3 to R5) needs the number. The error is
  already on `Acknowledge`; the loss is a single line.

## R3. A refusal stops the sequence

- **Today**: the match at `can_device.py:696-721` clears `board_ctx.uuid`,
  `repeated_command_count`, `prev_command`, `last_stim_output`, the
  `skip_uuid_ack_perf_c` flag and the `uuid_ack_timeout_engaged` property, then
  inserts the `_uuid_ack` entry. The next compound step is sent at `:872-891`,
  or the command is acknowledged at `:995` (V).
- **Must do**: a refusal is any `error` other than `0` and `-11`. For a refusal,
  do the resets at `:703-720` exactly as for an ACK, then **do not insert the
  `_uuid_ack` entry at `:702`**. Instead set `board_ctx.compound_steps = None`,
  clear `board_ctx.ctx` and `board_ctx.kind`, call the report in R4, and
  `continue`. Do not call `_acknowledge_command`. Leave the timeout path
  (`:743-798`) as it is: a timeout stays the only reason to resend. `-EAGAIN`
  takes today's success path unchanged.
- **Patterns to copy**: `_skip_lost_ack` (`:1008-1050`) already ends a command
  without an ACK and tidies the board context; `_clear_pending_commands`
  (`:1117-1146`) is the complete list of per-board fields.
- **Capture the command class before `:705` clears `prev_command`**, or better
  record it on `_BoardPendingContext` (`:141-165`) when the step is sent
  (`_perform_next_compound_step`, `:1656-1858`; `motor` is known at `:1833`;
  `predefined: send` is `FIXED_XYZ`, `:1759-1761`). R5 needs it.
- **What "stop" leaves behind (decide, see Decisions)**: the dropped steps may
  include cover, release, retract or servo steps. `PelletMachine` sets
  `_covered_state` optimistically when it queues the command
  (`pellet_machine.py:225`, `:233`), so after a refusal that state is a guess.
  Set it to unknown.
- **Why**: a refused `FIXED_XYZ` currently advances the trial as if the pellet
  was presented.

## R5. Name the codes, act per command class, tell the operator

The meaning of a code depends on the command, so key the action on
(command class, code). Compare the number, never the host's `errno`.

Name map: `-1 EPERM`, `-5 EIO`, `-11 EAGAIN`, `-16 EBUSY`, `-116 ETIMEDOUT`;
anything else is shown as "board error N". `Acknowledge.failure_reason`
(`device_interface.py:477-481`) says only "error N" today; give it the names.

**Stepper move, `FIXED_XYZ`, home**

- `-11`: success.
- `-1`: ESTOP is asserted. Stop. Do not retry. Do not release ESTOP from the
  host. The board marks every axis as needing a home (`stepper_power.c:151`), so
  after release a home is required. Nothing in reachAQ sends ESTOP:
  `SocketCanJerryCAN.EStop` (`socketcan_jerrycan.py:1010-1014`) has no caller and
  `CanInterface` has no ESTOP method (V). So a motion `-EPERM` means another
  client, such as the firmware's HIL script, or a stuck assert (I).
- `-5`: driver fault or drivers not proven. Stop. Mark every axis as needing a
  home. A home re-proves all three drivers and clears the fault (release note,
  "Faults and recovery"). A `-5` on the **home itself** has two causes the code
  cannot tell apart: a fault latched while the home ran, which another home
  clears, or drivers that did not re-prove, which only a board reboot clears
  (`board_reboot`, `can_interface.py:1968`), with the 12 V rail checked. So home
  once more, and reboot if that home is refused too. Never home a third time.
- `-116`: the board cut a move off after 30 s of silence. Mark every axis as
  needing a home (the host cannot tell which were moving; the board marks only
  those, `stepper_power.c:155`). It reaches the host only as the final ACK of a
  cut-off move or `FIXED_XYZ`. With O1 running, the cause is a host stall.
- `-16` on a **first send**: the axis needs homing after a stop. Stop. Mark it
  as needing a home. If the **home** returns `-16`, the axis is stuck (v2.3.0
  limitation 4 in the release note, unmeasured): reboot the board.
- `-16` on a **resend after an ACK timeout**: ambiguous. See R6.

**Servo move**: `-1` is ESTOP only (`servo.c:214`). `-16` means the servo is
moving, not "needs homing" (servos never home; `motor_motion_workq.c:607-610`).

**`GPIO_PULSE` and others**: `-1`/`-16` do not mean ESTOP or "needs homing".
Report as a refusal, mark no axis. What a refused pulse does to a trial is a
decision (see Decisions).

**Needs-home state**: keep `needs_home` per stepper in `HardwareModel`. Set it
in `_command_refused` for the stepper cases above. Clear it in `_ack_received`
when the popped token's command is `SEND_HOME`/`SEND_TO_LIMITS` (the pending
dict already stores the command, `hardware_model.py:101`, `:1316`). A home
that is ACKed clears the axes it covered; a home is one axis per step
(`can_device.py:421-424`, `:1779-1790`).

**Where the operator sees it** (today none of these shows a refusal):

1. Log: `CanDevice` logs the code name, command and token at ERROR (V).
2. Trial record: an active attempt is finalized as a hardware error with the
   text (`pellet_cycle_controller.py:246-262`; `HardwareErrorKind`
   `pellet_trial.py:98-103`), reaching `session_api.trial_ended` and the session
   summary. Hardware errors can never be counted as trials
   (`pellet_trial.py:120-122`) (V).
3. Banner or dialog: `AppModel.on_error(...)` (V that it exists; used at
   `app_model.py:1455-1563`). Needed for refusals outside an attempt.
4. Status panel: `hardware_status_content.py:306-355` builds the pellet rows
   (connection, health, firmware, compatibility). Add a "motors" row for
   needs-home and the last refusal.
5. Recording blockers: `app_model.py:3040-3055` already blocks Record on a
   firmware mismatch. Add a blocker while an axis needs a home or a fault is
   latched.
6. Session telemetry: the refusal kind and the `can_failure` device event
   (`hardware_model.py:1136-1148`) are recorded by the existing device-event
   path (V for the path; I that a new kind is kept).
7. API events: (U), see R4.

Suggested text (short, says what to do):

- `-1`: "Pellet motors are in E-stop. Release the E-stop, then home the pellet axes."
- `-5`: "Pellet stepper driver fault or drivers not initialised. Home the pellet axes to clear it. If the home is refused as well, reboot the pellet board and check the 12 V supply."
- `-16` first send: "Pellet axis <X/Y/Z> needs homing after a stop. Home the pellet axes."
- `-116`: "Pellet motors switched off after 30 s without host traffic and a move was cut off. Home the pellet axes."

No automatic retry of a refused command. Whether reachAQ may home on its own
afterwards is a decision for the owner (see Decisions): `move_home()` is already
called automatically on excessive drift (`system_machine.py:302`) and on pause
(`:471`).

## R6. A resend after an ACK timeout must not become a refusal

This is the one place where honouring errors **breaks existing behaviour**.

- **Today**: a command whose ACK times out is resent (`can_device.py:793-798`)
  with a **new uuid**. If the original is still running (a home slower than the
  timeout), the board refuses the resend at once with `-EBUSY`. The refused
  handler writes `context->uuid = msg->uuid` before refusing
  (`stepper.c:86`, `:346`), so the running move's eventual ACK carries the
  resend's uuid, and the original uuid is never ACKed (release note, known
  limitation 9) (V). The host treats the immediate `-EBUSY` ACK as success and
  starts the next step with the first axis still travelling. That already
  happens on v2.3.0.
- **After R3**: the same event ends the sequence with a hardware error while the
  axis is still completing a normal move.
- **Must do**: capture `repeated_command_count` before it is reset at `:704`.
  An `-EBUSY` on a command that has been resent (count > 0) is "still moving or
  unknown", not "needs homing". Options:
  - (a) Report it as `OPERATION_UNKNOWN`-class (like the transport-loss case,
    `hardware_model.py:1101-1119`), mark nothing as needing a home, and let the
    operator or the next trial proceed once the axis stops. Simplest.
  - (b) Keep `board_ctx.uuid` armed and wait for the second ACK on the same
    uuid. Depends on the firmware ACKing the resend's uuid at completion, which
    is read from code, not seen on a board (I).
  - (c) Avoid the resend: set each stepper's `uuid_ack_timeout` in
    `motor_config.yaml` above the longest home or move. Config only; no code.
  Recommended: (c) now, (a) in code.

# Recommended

## S1. Read `STEPPER_STATUS.status`

- **Today**: `_translate_stepper_status` (`can_interface.py:1921-1950`) builds
  `StepperStatus(target, motor, position, send_position, limit_switch,
  position_error=...)` and never reads `message.stepper_status.status`.
  `StepperStatus` (`device_interface.py:371-412`) has no field for it (V).
- **Must do**:
  - Add a keyword-only `status: int = 0` to `StepperStatus` (compatible with
    the constructors at `can_interface.py:1943`, `emulation_interface.py:126`,
    `can_device_test.py:1116`), expose `driver_fault` and `enable_off`, and
    fill it from `getattr(message.stepper_status, "status", 0)` (the
    `pyjerrycan` object may not carry it, U).
  - **Add `status` to the dedupe tuple at `can_device.py:1460`.** Otherwise a
    change in the status byte alone is dropped for up to
    `same_data_refresh_delay` (2.5 s, `:71-72`) or forever while position is
    unchanged (V).
  - Track it per motor in `HardwareModel._message_handler_property_changed`
    (`hardware_model.py:934-955`), expose a "pellet motor state" property, and
    show it in the pellet rows (`hardware_status_content.py:306-355`) and as a
    recording blocker (`app_model.py:3040-3055`).
- **How to read the bits** (from `stepper_power_policy.c:90-111`):
  bit 0 on any motor: driver fault latched, recover by home. Bit 1 alone on all
  three: ESTOP, drivers not proven, or host silent. Bit 1 on two motors and
  bits 0 and 1 on the third: a fault on that motor. `DRIVER_FAULT` is hidden
  while ESTOP is asserted (release note, limitation 3). `0x00` on v1.2.
- **Coupling with O1 (I)**: without a heartbeat, a v1.3 board shows
  `ENABLE_OFF` on all motors after 30 s idle and clears on the next host frame.
  Treat bit 1 alone as informational unless a command was refused or it
  persists for more than about a second after a host frame; otherwise every long
  inter-trial interval raises an alarm.

## S2. `validate_can_hardware.py` reports refused commands

`tools/hardware/validate_can_hardware.py` is the operator's tool in the
recovery procedure. `_require_success` (`:208-210`) tests only that the frame
was sent. `_listen` (`:150-161`) prints each translated message, including
`Acknowledge(... error=-5)`, but `main` returns 0. A refused `--action home`
looks like a success. Make `_listen` remember an `Acknowledge` with a non-zero,
non-`-11` error and have `main` exit non-zero naming the code.

# Optional

## O1. Heartbeat

- **Today**: `CanInterface.send_heartbeat()` (`can_interface.py:1471-1478`)
  sends a broadcast `HEARTBEAT` (`socketcan_jerrycan.py:1004-1008`, id low bits
  `0x1F`). Its only caller is `auto-trainer-device/tests/can_interface_test.py:60`
  (V). The 30 s clock-sync request (`can_device.py:593-601`) is addressed to the
  pellet, so it counts as host traffic to the board, but its period is at least
  30.0 s, equal to the board's 30 s timeout, so it cannot hold EN on (I).
- **Where**: in the command loop, next to the watchdog stamp
  (`can_device.py:671`), through `self._execute_if_active(
  self._interface.send_heartbeat)`. The loop wakes at least every 0.25 s
  (`:674-681`). **Not** in `_check_pellet_status_age` (`:589-608`): that thread
  survives a dead command thread and would keep a stalled host's motors enabled,
  defeating the board's dead-man timer. (My judgement.)
- **Period**: 5 s. The board's timeout is 30 s and its range 5 to 600 s; the
  host cannot read it. Use at most a third of the configured value.
- **Gating**: add `CanDevice.heartbeat_period_s: Optional[float] = None` and set
  it from `HardwareModel` after the capability check (`hardware_model.py:698-704`)
  when bit 6 is reported, so v1.2 rigs and tests are unchanged.
- **Needs a handler**: the board answers each heartbeat with a `HEARTBEAT`
  (`heartbeat.c:50-60`). `Heartbeat` has no entry in `_data_handlers`
  (`can_device.py:535-567`), so every reply would log
  `Unhandled data type` (`:1432`). Add `Heartbeat: _no_op_handler`.
- **Side effects**: the broadcast reaches every board and blinks its LED; the
  IO module's replies also arrive.
- **Why I would move this to Recommended if** the firmware's `silence_cycles`
  check shows lost steps at the enable edge. Without a heartbeat, every
  inter-trial gap over 30 s takes that edge, and the release note says a move
  right after the restore "has not been shown on a board". A single move or
  home longer than 30 s with no host frame is also cut off with `-ETIMEDOUT`;
  the longest home on a rig is (U).

# Existing code that depends on errors being ignored

1. **Timeout resend gets `-EBUSY` and carries on.** `can_device.py:793-798`
   with `stepper.c:86`, `:346`. Becomes R6. Already wrong on v2.3.0. (V code,
   I effect.)
2. **`-EAGAIN` is routine.** `default_move_retract` sends `send_z_rel: 0`,
   `send_x_rel: 0`, `send_y_rel: -15` (`can_device.py:1934-1936`), each an
   absolute move to the last send position (`:1554-1562`); an axis already
   there ACKs `-11`. `default_load_pellet` starts with `{'x': 0.0}` (`:1870`).
   `FIXED_XYZ` does not report `-EAGAIN`. Treating `-11` as a refusal would
   fail ordinary retracts. (V)
3. **A refused `SEND_PELLET` is counted as presented.** `pellet_machine.py:401-405`
   then `app_model.py:12050-12092`. (V)
4. **Connect reaches "ready" with refused homes and config writes.**
   `hardware_model.py:665-691`, `:728`, `:745`; `device_connection.py:242-266`.
   (V)
5. **A refused stimulus pulse is recorded as acknowledged.** `Acknowledge`'s
   docstring and commit `f627d599` say so. After R3 a refused pulse stops the
   sequence and the trial is a hardware error, where today it continues
   unstimulated. `_skip_lost_ack` (`:1008-1050`) deliberately continues, but only
   for a **missing** ACK; a refusal means the board did not pulse. Decision below.
6. **v1.2 rigs on 2.3.0 or 2.3.1 may start failing.** Honouring errors is not
   gated on bit 6. Release-note limitation 4 says a home that travels to its
   switch can leave the axis stuck at `-EBUSY` "until a reset"; today the host
   ignores that. If it happens on a healthy rig, the first refusal will appear
   right after the connect home. Run R3 first on a known-good v1.2 rig. If
   `-EBUSY` shows up there after a normal home, stop and tell the firmware side;
   do not make the host ignore `-EBUSY`. (U: unmeasured.)
7. **`validate_can_hardware.py` exits 0 on a refusal.** S2.
8. **`tools/pellet_delivery` and `can_console`** clear "command pending" on ACK
   only (R4).
9. **Anything that unpacks the ACKNOWLEDGE tuple as two values**
   (`message_handler.py:127`, `can_device_test.py:1037`) breaks if it is
   widened; hence the new kind.

# The post-update operator procedure

The brief says the pellet's settings-partition bug forces, after any firmware
update: rewrite the motor config with
`tools/hardware/validate_can_hardware.py --action write-motor-config
--allow-config-write --motor x|y|z` (default `--motor-config
~/Autotrainer/motor_config.yaml`, `validate_can_hardware.py:138-143`), and
re-save the FIXED_XYZ positions. I did not verify the bug itself (U).

What the host code shows (V):

- A normal reachAQ start **already rewrites** that file to the board for every
  required motor: `hardware_model.py:710` calls `load_default_motor_config`
  (`device_connection_protocol.py:59-70`), which writes through
  `use_motor_configurations` (`device_connection.py:242-266`), then homes
  (`:728`). So for a rig that starts reachAQ after the update, the config half
  of the procedure happens anyway. The validator action matters for bench use
  without reachAQ.
- If `~/Autotrainer/motor_config.yaml` is **missing**, connect applies the host's
  defaults instead (`device_connection_protocol.py:64-68`; defaults such as
  `microsteps = 64`, `device_interface.py:286-291`) and logs a warning. That
  would overwrite a correct board config.
- The fixed positions are not written at connect by anything I traced. reachAQ
  holds per-animal base positions (`app_model.py:10635-10665`) and saves them
  with `SET_X/Y/Z` (`can_interface.py:1224-1226`, `save_as_fixed`). Where it
  re-sends them on connect or animal selection was not traced (U). The board
  reports its current fixed position in every status frame as `send_position`
  (`stepper.c:376`), which reachAQ keeps as `send_x/y/z`
  (`hardware_model.py:940-955`).
- The validator can do the re-save: `--action set-x|set-y|set-z --position <mm>
  --allow-motion` calls `set_motor_*`, which is save-as-fixed
  (`validate_can_hardware.py:81-86`).

**Suggestion (O2, not a requirement)**: reachAQ could warn at connect.

- Between reading the board's config (`can_interface.py:782` ->
  `_query_configuration`, `:1046-1055`) and the write (`hardware_model.py:710`),
  compare board vs file field by field and log a WARNING per difference: "board
  config differed from the file; settings may have been lost (firmware
  update?)".
- After the connect home, compare `hardware.send_x/y/z` with the selected
  animal's base position and warn on a mismatch.
- Persist the last firmware version seen per rig under `~/Autotrainer` and warn
  once when it changes: "firmware changed X to Y: re-save FIXED_XYZ positions".

# Decisions for the owner

1. **Auto-home after a refusal**: never, between trials, or on an operator
   click. A home drives all three axes to their switches. The host already
   homes on drift and on pause.
2. **A refused stimulus pulse**: stop the trial (consistent with R3), or
   continue unstimulated as today. The first records a hardware error instead of
   a silently unstimulated trial.
3. **Resend `-EBUSY`**: (a), (b) or (c) in R6.
4. **What "stop" leaves behind**: after a refused step, run a cleanup of the
   cover and load servos, or leave them. Today nothing runs.
5. **New message kind** (R4) versus the narrower `failure_callback` route.
6. **Heartbeat** (O1): in, and gated on bit 6, or later.

- **Read, not run.** No reachAQ test was run; no board was used. v2.3.1 itself

- **Not inspectable**: the compiled `pyjerrycan` module (does `msg.ack.error`

- **Firmware coverage**: I read `stepper.c`, `servo.c`, `tone.c`,

  surface as a hardware error. If in doubt, scope R3 to motion commands first.
