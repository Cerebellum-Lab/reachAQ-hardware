**Pellet v1.3 boards need at least this version.** On v1.3 the shared stepper
enable (`~EN`) is pulled high through R41, so the three drivers stay disabled
until firmware drives PD2 low. Firmware through v2.3.0 never does. A v1.3 board
on v2.3.0 or older accepts moves and does not move.

**Build v2.3.1 on top of the storage-partition fix
([#3](https://github.com/Cerebellum-Lab/reachAQ-hardware/pull/3)).** On the
layout this branch and v2.3.0 share, the board's stored settings (motor
configuration and saved `FIXED_XYZ` positions) do not survive a reboot or an
update (see "Findings"). With that fix in the image, the first update to v2.3.1
loses the stored settings once, because the store moves to a new address.
After that they persist across reboots and updates. After the first update,
rewrite the motor configuration (reachAQ does this when it initializes the
hardware, but not a reboot mid-session) and re-save the `FIXED_XYZ` positions.

With today's host, a v1.3 rig's EN goes off after 30 s with no frame addressed
to the board, and the next host frame restores it. That is expected, and idle
motors are unaffected: the drivers already leave an idle axis unheld (see
"Known limitations"). That a move sent right after the restore lands correctly
has not been shown on a board; the v1.3 checks (`silence_cycles`) must show it.

## Changes

- Drive the v1.3 board's shared stepper enable (`~EN` of U2, U5 and U6, active
  low, on PD2) and watch the drivers' DIAG outputs: PF1 for U2, PB2 for U5 and
  PB10 for U6. The DIAG index is the motor id, so U2, U5 and U6 are `stepper0`,
  `stepper1` and `stepper2`. At boot PD2 is sampled once with the internal
  pull-down on; R41 (5.1 kOhm to 3V3) makes it read high on v1.3, which is how
  the board knows it has an enable net. EN is shared and board-wide, with no
  per-move enable, and stays off until all three drivers have proven over UART
  that they took their configuration.
- Report faults in the `status` byte of `JERRYCAN_CMD_STEPPER_STATUS` (`0x16`),
  which has been a constant 0, and advertise that as capability bit 6.
- Handle `JERRYCAN_CMD_ESTOP` (`0x00`), take EN off after 30 s with no frame
  addressed to the board, and recover from a fault with a re-home that
  re-proves all three drivers first. The final ACK of an interrupted move says
  why, and the final ACK of `FIXED_XYZ` reports the first axis refused.
- Take EN off in a fatal error handler for the pellet image, before halting.
- Make a stopped motor able to move again (the new stop path stops the DMA and
  the stepper's timer counter and drops every queued block), and fix two bugs
  that the new stop paths now reach: `motors_all_stop` passed a stepper device
  to `servo_motor_stop`, and `set_all_e_stop_flags` set the stepper flags twice
  instead of the servo ones.
- Set the pellet main stack to 1536 bytes (`CONFIG_MAIN_STACK_SIZE`, not set
  before): the re-proof path was estimated to leave 32 to 88 bytes of margin.
- Add the `ll,stepper-power` binding and a `stepper_power` node on the pellet
  board. The feature compiles only where that node exists, so the magnet and IO
  module images do not build it. Two `motor_math` shell commands are new.

## Wire protocol

No new frame and no layout change. `JERRYCAN_WIRE_SCHEMA_VERSION` stays `1`.

`JERRYCAN_CMD_STEPPER_STATUS = 0x16`, board to host, 12 bytes, unchanged:
`motor_id`, `status`, `homing_status`, `limit_switch`, `position`,
`send_position`. One frame per stepper every 100 ms. Only `status` changes
meaning:

| Bit | Name | Meaning |
| --- | --- | --- |
| `1 << 0` | `DRIVER_FAULT` | This motor's driver raised DIAG; latched until a re-home |
| `1 << 1` | `ENABLE_OFF` | The shared enable is off, for any reason |

The value for each motor is the first row that matches:

| Condition | `status` of the motor |
| --- | --- |
| No enable net (v1.2) | `0x00` |
| ESTOP asserted | `0x02` |
| Drivers not proven configured | `0x02` |
| A fault is latched | `0x03` for each driver that faulted, `0x02` for the others |
| Host silent | `0x02` |
| Otherwise | `0x00` |

`ENABLE_OFF` alone does not say why EN is off. The ACK error does (below). "Not
proven" ranks above a latched fault, so after a re-home whose proof fails, the
`DRIVER_FAULT` bit goes away while moves keep being refused with `-EIO`.

`JERRYCAN_CMD_ESTOP = 0x00`, host to board, 1 byte `rsvd` (`uint8`): non-zero
asserts ESTOP, zero releases it. The field is named `rsvd` in
`jerrycan_types.h`; this firmware reads it as the assert flag. The arbitration
id is the board address, or `0x01F` to broadcast. ESTOP is one-shot and draws no
ACK.

## Capability bits

| Bit | Name | Set by this firmware |
| --- | --- | --- |
| `1 << 0` to `1 << 3` | | As in v2.3.0: only `FINITE_GPIO_PULSE` (`1 << 2`) is set, where the board has a pulse counter |
| `1 << 4`, `1 << 5` | | Used by `feat/pellet-board-timing` and `feat/io-module-firmware`; not defined here |
| `1 << 6` | `STEPPER_DRIVER_FAULT` | Yes, on a board that found its enable net at boot |

A pellet v1.2 answers `0x00000004`, a pellet v1.3 `0x00000044`. Bit 6 means the
board found the enable net at boot. It rests on a single sample of PD2, so a
v1.3 board that sampled low would leave it clear and behave as a v1.2 board:
moves accepted, motors disabled. It does not mean the drivers were proven or
that EN is on. The boot log line `Capabilities 0x...` does not show bit 6,
because the bit is added per request; read it from the response.

## ACK errors

The `error` field of `JERRYCAN_RSP_ACK` is the firmware's errno, as a negative
number. The build uses picolibc (`CONFIG_PICOLIBC=y`), which defines these
values, and they are not all Linux's. `ETIMEDOUT` is 116 here and 110 on Linux,
so a host must compare against the number and not against its own
`errno.ETIMEDOUT`.

| Value | Name | Meaning on the pellet |
| --- | --- | --- |
| `-1` | `EPERM` | ESTOP is asserted. Stepper moves, homes and servo moves are refused. A move that ESTOP interrupted ends with it |
| `-5` | `EIO` | A driver fault is latched, or the drivers were not proven configured. Refused until a re-home succeeds (fault) or the board reboots (not proven) |
| `-11` | `EAGAIN` | The target is within 1/microsteps turn of the axis's last generated position (0.125 turn at microsteps 8): the axis is already there. Not a failure, and not new: v2.3.0 answers it the same way |
| `-16` | `EBUSY` | The axis is already moving, or the axis needs homing |
| `-116` | `ETIMEDOUT` | EN is off because the host went silent |

A refused `STEPPER_MOVE` or `STEPPER_HOME` is ACKed at once with the error. So
is a `STEPPER_MOVE`, absolute or relative, whose target is within 1/microsteps
turn of the axis, with `-EAGAIN`, on a healthy board and on a v1.2 board
(`motor_motion_workq.c:758`, `modules/stepper.c:110`). A move that was already
running when it was stopped gets its ACK on the next status tick (100 ms), with
the board-wide error at that moment; a move that finished normally just before
a fault or an ESTOP, inside the same tick, can also ACK with it. A command that
arrives after the board went silent is not refused with `-ETIMEDOUT`, because
the frame ends the silence before its handler runs. So `-ETIMEDOUT` reaches a
host only as the final ACK of a move the silence cut off, or of a `FIXED_XYZ`
still working through its axes.

`FIXED_XYZ` has one ACK for three axes, and visits them in the order X
(stepper 0), Z (stepper 2), Y (stepper 1). It reports the first axis in that
order that was refused: `-EPERM`, `-EIO`, `-ETIMEDOUT`, or `-EBUSY` when that
axis was not already moving. An axis already at its target (`-EAGAIN`) does not
count. If no axis was refused, it reports the board-wide error at that moment,
which is 0 when nothing is wrong.

## ESTOP

- Asserting stops every moving stepper and servo (DMA and counter stopped,
  queue dropped), marks every axis as needing a home, and takes EN off (v1.3).
  It stays asserted until a frame with payload 0 arrives. It is held in RAM, so
  a reboot also releases it.
- While asserted, stepper moves, homes and servo moves are refused with
  `-EPERM`, and a v1.3 board reports `ENABLE_OFF` for every motor.
- On release, EN returns if nothing else holds it off: the drivers are proven,
  no fault is latched, and the host is not silent. Every axis still needs a
  home, so a move is refused with `-EBUSY` until that axis has been homed.
- `JERRYCAN_CMD_STATUS` (`0x01`) is not transmitted by this firmware, so ESTOP
  shows only in the stepper `status` byte and in ACK errors.
- On a v1.2 board ESTOP still stops motion and refuses moves with `-EPERM`;
  there is no EN to drop and the status bits stay 0. No host sends ESTOP today.
- After an ESTOP, a servo's `last_position_generated` is the planned end of the
  stopped move (for a move short enough to be generated before it starts), and
  the next servo move starts its profile there. Its first sample therefore jumps
  to the old target at the servo's full speed. Servos never home, so nothing
  clears this. Two things reach this path: ESTOP (`motors_all_stop()`,
  `motor_motion.c:68`) and the shell command `motor_math servo_stop`
  (`motor_motion_shell.c:184-185`), which stops a servo the same way.
  `SERVO_STATUS` reports the same planned position afterwards, not where the
  servo is.

## Host silence

- The timeout is 30 s (`CONFIG_LIB_MOTOR_MOTION_HOST_SILENCE_TIMEOUT_MS`,
  range 5000 to 600000; the pellet does not override the default), counted from
  the end of the driver proof at boot. The poll runs every 100 ms, so EN goes
  off up to about 100 ms after the 30 s mark.
- A frame counts if the low five bits of its arbitration id equal the board's
  address or `0x1F`. The test comes before the command type is read, so
  `HEARTBEAT`, `CAPABILITIES_REQUEST`, `CFG_READ` and a type the board does not
  know all count, and so do the shell commands `motor_math stepper_move` and
  `stepper_home`.
- On silence the board takes EN off, stops any stepper that was moving and
  marks only those steppers as needing a home. Servos are not touched. Status
  is `ENABLE_OFF` for every motor.
- The next frame addressed to the board puts EN back on, with a 1 ms settle,
  before its command runs. The datasheet (rev 1.09) states no delay from ENN
  low to the first step, so the 1 ms is a margin.

## Faults and recovery

DIAG is the OR of stall detection, driver power-on reset, charge-pump
undervoltage, overtemperature, and a latch set by shorts and overtemperature
(datasheet rev 1.09, Figure 15.1). ENN high resets only that latch. The
firmware keeps StallGuard off (`SGTHRS = 0`, `TCOOLTHRS` unwritten), so stall
detection does not fire. A fault can therefore also mean that a driver reset
or that the supply dipped, not only a short or overheating.

- A reading counts only while EN is on, and only if it is high on two
  consecutive 100 ms polls. A DIAG still high after EN goes off (undervoltage,
  overtemperature) shows again once EN returns.
- On a latched fault the board stops the steppers, reads DRV_STATUS and GSTAT of
  each faulted driver and logs the flags set (`ot`, `otpw`, the four shorts,
  `drv_err`, and `uv_cp` and `reset`, the two DIAG causes that set no
  DRV_STATUS flag), marks all axes as needing a home, and takes EN off last.
  The cause goes to the console log only, not the wire. Moves are refused with
  `-EIO`.
- A `STEPPER_HOME` for any axis recovers. Before EN returns, the board
  re-proves all three drivers: `IFCNT` must advance by exactly one when
  `IHOLD_IRUN` is rewritten with init's values, `GCONF` `pdn_disable` and
  `mstep_reg_select` must still be set, and `GSTAT` `reset` must be clear. By
  count that is 15 register accesses at 10 ms each, about 150 ms added to the
  home; it has not been timed. A driver that fails is checked once more before
  it counts as failed, so one UART glitch does not refuse motion; a driver that
  really reset fails again, because the proof does not rewrite `GCONF`.
- If all three pass, the fault latch clears for all three drivers and EN
  returns. Only the homed axis is homed. The others are still refused with
  `-EBUSY` until each is homed.
- If any driver fails both attempts, motion is refused with `-EIO` until a
  reboot. A further home repeats the check and is refused again. If DIAG is
  still high after a successful re-home, it latches again two polls after EN
  returns.
- Boot runs the same proof before EN first goes on. A driver that fails both
  attempts leaves EN off and motion refused with `-EIO` until a reboot.

## Fatal errors and shell

A fatal error on the pellet (a CPU exception, a stack overflow, `k_oops()`,
`k_panic()`, an unhandled interrupt) now takes EN off with one GPIO write, then
halts exactly as Zephyr's handler does. A halt leaves interrupts locked, so the
DMA completion that stops a stepper's timer cannot run and STEP likely keeps
pulsing (reasoned from the code, not measured). A reset is not used, because it
would change v1.2 behavior. The handler has never run: `fault_safety.c` is
compile-checked only.

- `motor_math stepper_power_status` prints the enable state, then runs the
  driver proof on each driver; on v1.2 that is the only driver-proof traffic.
- `motor_math stepper_power_oops` triggers a fatal error on purpose, to show
  that EN goes off. It halts the board, on either hardware revision.

## Behavior on a v1.2 board

With no enable net detected the module logs `no stepper enable net`, sets PD2
to disconnected, and from then on touches no pin and adds no UART traffic. It
does not configure the DIAG pins, install the frame hook, or schedule the poll.
Bit 6 is clear and every `status` byte is 0, as before. None of the new
refusals can occur there unless an ESTOP is sent, so `FIXED_XYZ` and single
moves ACK as in v2.3.0. What a v1.2 board does carry: the ESTOP handler, the
fatal error handler (no pin touched), the 1536 byte main stack and the shell
commands.

## Known limitations

1. The ACK error is sampled at the next 100 ms status tick, not at the stop, so
   a stop that is undone before the tick can ACK 0. Two cases: a single move
   interrupted by an ESTOP that is released within one tick (it takes a pulse
   shorter than the tick), and a move cut off by silence followed by any frame
   to the board before the tick, because that frame ends the silence. The
   window in both is up to 100 ms. `FIXED_XYZ` has the same hole: an axis is
   cut off by silence, a frame arrives inside the tick, the remaining axes run
   (the needs-a-home flag is set only on the stopped axis), and the final ACK
   is 0.
2. `-EBUSY` means either "axis already moving" or "axis needs homing". Host
   code cannot tell them apart from the number alone. `homing_status` in the
   status frame is the current move type, not whether a home is owed.
3. The `DRIVER_FAULT` status bit is hidden while ESTOP is asserted. It
   reappears on release. `ENABLE_OFF` still shows.
4. Every home that travels to its switch (`motor_motion_workq.c:295`), and
   any other move that a limit switch stops, keeps two behaviors from v2.3.0.
   A block left in the queue can leave the axis stuck at `-EBUSY` until a
   reset, and the timer keeps running, so the next move may emit a few
   unplanned step pulses while its table is computed. On a rig that next move
   is the first one after every home. The shell `stepper_stop` takes the same
   route. This is pre-existing, has not been measured on hardware, and is left
   unchanged because a fix would shift v1.2 positions. The ESTOP, fault and
   silence stops drop the queue and stop the counter, so they do not have this
   problem.
5. Homing has no timeout. With a dead limit switch and a live host, the motor
   runs until someone stops it. Host silence only covers a dead host.
6. A driver reset shorter than two 100 ms polls goes unnoticed. It leaves that
   driver at its power-up defaults (`IRUN = 31`) with EN on, and nothing
   notices until a fault latches and a re-home re-proves it. The shared 12 V
   rail should make a short dip unlikely, but this has not been measured.
7. The magnet image has not linked since v2.3.0: `z_impl_sys_rand_get` is
   undefined, because `capabilities.c` needs an entropy driver that the magnet
   `prj.conf` does not enable. Unrelated to this change and out of scope; the
   magnet image can only be compile-checked.
8. No watchdog runs on the pellet. `&iwdg` is enabled in the devicetree and
   nothing feeds or starts it, so a hang that is not a fatal error leaves EN as
   it was.
9. A command that arrives in the window of up to 100 ms between a stop and the
   next status tick can be ACKed twice, and the interrupted move's uuid is
   never ACKed. A refused command writes `context->uuid` before it is refused
   (`stepper.c:86` for a move, `stepper.c:346` for a home), so the tick that
   follows ACKs the new uuid for the stopped axis as well. This pattern is
   pre-existing and is left, because fixing it would change v1.2 retry
   behavior.
10. Two axes interrupted together give only one ACK, because `moving_state`
    goes to `MOVING_NONE` after the first (`stepper.c:184-190`). Pre-existing.
    reachAQ reaches it only after a home that outlasts its ACK timeout (3 s by
    default) is retried and the next home starts.

Also found by reading the code, not measured:

- A silence stop marks only the steppers that were moving as needing a home.
  An axis that was idle stays marked homed. That is not new with silence: the
  firmware writes `IHOLD` register 0 and `freewheel = 1` to every driver
  (`adi_tmc2209.c`), on v1.2 too, so an idle axis is already unheld whether EN
  is on or off. A silence stop changes nothing for it, and the stale-position
  risk is the same as at any idle moment.
- An ESTOP frame that arrives while the board is silent puts EN on for about
  1 ms (the settle) before the handler takes it off again. Nothing steps in
  that time.

## Acceptance criteria

Each is a thing to see on a board before the release is tagged. Only part of
the v1.2 list has been seen, in the rig run below: `capabilities = 0x00000004`,
every `status` byte 0 while idle, and home and move ACK 0. Nothing else here
has been checked.

- Both: the version request reports `2.3.1` after reboot and finalization.
- v1.2: boot log `no stepper enable net`; `capabilities = 0x00000004`; every
  `status` byte 0, idle and moving; home, move and `FIXED_XYZ` ACK 0 as on
  v2.3.0.
- v1.3: `capabilities = 0x00000044`; `boot_id` stable within a boot. With a
  frame reaching the board every few seconds, all three `status` bytes are 0
  and the motors move on command.
- v1.3, 30 s with no frame addressed to the board: all three `status` bytes
  `0x02`. The next frame brings them back to 0, and a move works.
- v1.3, ESTOP during a move: that move ACKs `-1` once, and a move sent while
  asserted is refused with `-1`. After release a move is refused with `-16`
  until the axis is homed, then works.
- v1.3, DIAG forced high on one driver: the move in progress ends with ACK
  `-5`; that motor's `status` is `0x03` and the others' `0x02`; a further move
  is refused with `-5`; a home clears all of it.
- v1.3: `motor_math stepper_power_oops` takes EN off (PD2 high) before the board
  halts.

## How to verify on a rig

Capabilities, as for v2.3.0: request `0x460`, response `0x480`, nine payload
bytes with the last four the boot id. v1.2: `01 04 00 00 00 xx xx xx xx`. v1.3:
`01 44 00 00 00 xx xx xx xx`. Stepper status frames are on `0x2C0` for address
0 (`0x16 << 5`); byte 1 of the payload is `status`.

The rest is `firmware/lib/motor_motion/test/hil_stepper_power_check.py`, which
covers the capability, status, ESTOP, fault and silence items above (not the
version request or the fatal error handler). **It moves the motors.** Close
reachAQ first, and keep the stage clear. Its ESTOP goes to the board's own
address, never to the broadcast address `0x1F` that the host library's
`EStop()` uses, so other modules on the bus are not stopped. The pellet counts
either as a host frame and dispatches on type, but the broadcast form is not
exercised. A home that gets no ACK, Ctrl-C, SIGTERM and SIGHUP make the script
assert and release ESTOP at the board and leave every axis needing a home.
Only firmware from this branch handles ESTOP. On v2.3.0 and older it does
nothing, and a v1.2 board reports the same capabilities on both, so the script
cannot tell which it is talking to: against a v2.3.0 baseline, be ready to cut
power.

```bash
python3 firmware/lib/motor_motion/test/hil_stepper_power_check.py --board v1.3 --channel can0 --address 0
```

Use `--board v1.2` for a v1.2 board. `diag_fault` needs `--axis N` and an
operator to force DIAG; `silence_midmove` needs a 5 s silence build (see
`--help`).

`silence_cycles` runs 30 cycles, about 17 minutes at the default 32 s quiet, 16
of them the silences (it prints its estimate). `--cycles` must be a multiple of
3 and at least 3, so that every axis moves: an axis that has not moved sits at
0, and the 0.1 turn move to it falls under the 0.125 turn same-position gate and
ACKs `-EAGAIN`. Each cycle waits out the silence, checks `ENABLE_OFF` on
all three motors, and moves one axis +0.25 turn, rotating the axes. Each axis
ends 2.5 turns from its switch, so steps lost at the enable edge add up in one
direction. Each axis then goes back to 0.1 turn short of its switch, where the
switch must read open, and 0.2 turn further, where it must hit. A net loss or
gain of more than 0.1 turn on an axis fails.

After every check the script audits the ACKs it has received: one whose uuid it
never sent as a command, or a second ACK for a command, is a FAIL naming the
uuid. `estop_multiblock_restart` runs on axis 2 by default, and `--axis`
overrides that, because a stop that ACKs an idle axis's stale uuid shows only
when the moving axis is not axis 0. It moves the smallest distance over 1.25
DMA blocks (1280 pulses, so 6.67 turns at 24 steps per revolution and
microsteps 8, and 3.33 turns at 48), because it needs only a second block still
queued when the ESTOP lands. It skips if that is further than `--max-turns`
(default 8), or if the profile puts the ESTOP at 1024 pulses or more, and it
homes the axis again at the end; that home must ACK 0 for the check to pass.

Exit status: 0 only if every selected check passed, 1 on any FAIL, 2 for bad
arguments, and 3 if nothing failed but something was skipped, with a line
naming what. A default run therefore exits 3: `diag_fault` and `silence_midmove`
skip without their options, and on a v1.2 board three checks always skip.

The script ran against a CAN interface several times on 2026-11-09: on v2.3.0
baselines, on the development image as it was at `c5b09b0`, and in the two
queued runs with the script at `9636220`, which is identical to `596f3c2` (see
below).
`motor_math stepper_power_status` on the serial console shows the state.

## Rig run, 2026-11-09 (v1.2 board, christielab10)

### First run

A development image built from `c5b09b0` was flashed to the rig's v1.2 board
after the user approved it, and the check script as it was at `c5b09b0` ran on
it. The board reports version 2.3.0 because the version comes from `git
describe` and there is no `v2.3.1` tag. This is not a release and not a
deployment.

- Pass: `capabilities` (`0x04`), `status_idle`, `home_and_move`,
  `estop_multiblock_restart` and `recover_at_limit`.
- On `estop_multiblock_restart`: the ESTOP went out 0.61 s after the move frame,
  the move ACKed once, `-EPERM`, at 0.68 s, the move was 2560 pulses (13.33
  turns on axis 2), and the restart move after the re-home ACKed 0.
- Fail: the cleanup re-home of Z, reported as `recover_at_limit/rehome`. Z did
  not reach its switch in 10 s from 13.3 turns, and the script stopped it with
  ESTOP. The cause is not proven. `estop_multiblock_restart` sent Z 13.33
  turns, about 32.5 mm of its roughly 35 mm of travel, and left it there.
  `596f3c2` caps that distance: it now moves just over 1.25 blocks (6.67 turns
  on this rig), skips if that is more than `--max-turns`, and homes the axis
  afterwards. The queued run's re-homes passed (second run, below).
- Not run: `fixed_xyz_interrupted` and `servo_after_estop`.

The v1.3 checks have not run: no v1.3 board has had this firmware on it, so the
enable, the status bits, the fault path and the silence cycles are all
unobserved.

### Findings

Two findings from the runs, both pre-existing and neither caused by this branch:

- The board's stored motor configuration (microsteps, steps per revolution,
  velocities, the limit orientation, and the saved `FIXED_XYZ` positions, which
  read 100.0 after one flash in the first run and 0 in the second) does not
  survive an image update, and does not survive a plain reboot either. In the
  pellet devicetree `storage_partition` (64 KB at 0x10000) lies inside
  `slot1_partition` (444 KB at 0x0), and has since `1cd915c`: an image download
  overwrites the store, and the settings store then fails to mount over the
  image bytes in slot 1. The storage-partition work confirmed the reboot case on
  christielab10 on 2026-11-09: a motor configuration written, a CAN reboot, and
  the configuration read back at defaults. Until the fix is in the image,
  rewrite the configuration after every reboot or update, or the board runs on
  firmware defaults; on the rig that sent X away from its switch when homing.
  `fixed_xyz_interrupted` skips while `send_position` is outside 0 to 15 turns,
  or 0 on all three axes.
  The fix is [#3](https://github.com/Cerebellum-Lab/reachAQ-hardware/pull/3),
  not this branch. It moves `storage_partition` to 0x100000 and corrects the
  flash size. That work reports the configuration surviving a plain reboot and
  a CAN update between two test images; see that PR.
- v2.3.0 ignores ESTOP, so on a board running it the remote way to stop motion
  is a bootloader REBOOT command over CAN.

## Host work

None of this is done by this change, and today's reachAQ cannot see a fault.
`_handle_ack` (`can_device.py:982-993` on `devel`) passes only the uuid and the
arrival time of an ACK to the command loop, so `ack.error` is dropped.
`Acknowledge.is_failure` and `failure_reason` have no caller outside tests, and
the stepper `status` byte is not read either. A fault, an ESTOP or an unhomed
axis therefore looks like success to reachAQ: a refused move advances the
compound sequence, and a later home clears the latch unnoticed. The note near
the top says what a quiet rig does.

- **Required to run it.** Add `2.3.1` to
  `config/pellet-firmware-compatibility.yaml`, and run `reachaq-sync` on each
  rig before flashing. reachAQ refuses a firmware version it does not list, and
  the updater will not flash one.
- **Required before deploying v1.3 boards.** Act on `ack.error`. Forward it
  from `_handle_ack`, and stop a compound sequence on an error ACK instead of
  advancing it, except `-EAGAIN` (-11). `-EAGAIN` means "already there" and is
  not a failure: a move within 1/microsteps turn (0.125 at microsteps 8) of the
  axis's last generated position gets it on a healthy board, on v1.2 and v2.3.0
  as well (`motor_motion_workq.c:758`, `modules/stepper.c:110`), so a host that
  stopped on every non-zero error would stop a healthy sequence. Without this, a
  v1.3 rig cannot tell a refused move from a finished one, and its motors can be
  off (silence, fault, ESTOP) while every command still looks successful. It is
  not required to run v1.2 boards on this firmware: they have no enable net, so
  none of the new refusals can occur there unless an ESTOP is sent, which no
  host does. They still return `-EBUSY` and `-EAGAIN` as they did on v2.3.0.
- **To use the reports.** Add `stepper_driver_fault: 1 << 6` to
  `CAPABILITY_BITS` in `tools/acquisition/model/firmware_compatibility.py`, and
  read `stepper_status.status` in `_translate_stepper_status()` in
  `auto-trainer-device/src/autotrainer/device/can_interface.py`. Today a fault
  is invisible to reachAQ: the ACK error is dropped and `status` is not read.
- **To recover.** reachAQ must re-home after a fault, and treat `-EBUSY` as
  "needs homing". The compound `home` already exists.
- **To guard old firmware.** The flash path could refuse an image below 2.3.1
  when the running board reports bit 6. A revert on a v1.3 board lands on
  whatever the other MCUboot slot holds; if that is older than 2.3.1 the motors
  stay disabled. The v2.3.0 deployment flashed twice for this reason.
- **To keep EN on while the host is idle.** Separate from the items above, and
  optional. Call the existing `send_heartbeat()` (`can_interface.py`, on
  `devel`; no caller outside tests) every few seconds. A `HEARTBEAT` counts as
  host traffic automatically. The IO module needs it anyway.
