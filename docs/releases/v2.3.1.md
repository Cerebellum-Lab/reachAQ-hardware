# Pellet firmware v2.3.1

**Not released.** There is no `v2.3.1` tag and no release date. The code is
compile-verified only: the pellet image builds with no warnings, and the enable
policy's rules table has host C tests. Neither hardware run has happened: not
the run on a v1.2 board, which shows that nothing changed there, and not the
checks on a v1.3 board, which show that the feature works. Everything below is
what the code does, read from `5a0df7a`. None of it has been observed on a
board. The release date and source commit are left as markers, to be filled

**Pellet v1.3 boards need at least this version.** On v1.3 the shared stepper
enable (`~EN`) is pulled high through R41, so the three drivers stay disabled
until firmware drives PD2 low. Firmware through v2.3.0 never does. A v1.3 board
on v2.3.0 or older accepts moves and does not move.

## Changes

- Drive the v1.3 board's shared stepper enable, `~EN` of U2, U5 and U6, active
  low, on PD2. At boot the board samples PD2 once with the internal pull-down
  on. R41 (5.1 kOhm to 3V3) makes it read high on v1.3, and that is how the
  board knows it has an enable net. EN stays off until all three drivers have
  proven over UART that they took their configuration, then goes on.
- Read the drivers' DIAG outputs every 100 ms: PF1 for U2, PB2 for U5 and PB10
  for U6. The DIAG index is the motor id, so U2, U5 and U6 are `stepper0`,
  `stepper1` and `stepper2`. A driver whose DIAG reads high on two
  consecutive polls while EN is on is latched as faulted.
- On a latched fault, stop every moving stepper, mark every axis as needing a
  home, take EN off, and log the cause on the console.
- Report this in the `status` byte of `JERRYCAN_CMD_STEPPER_STATUS` (`0x16`),
  which has been a constant 0, and advertise it as capability bit 6.
- Handle `JERRYCAN_CMD_ESTOP` (`0x00`) on the pellet, for steppers and servos.
- Take EN off when no frame addressed to the board has arrived for 30 s, and
  put it back on the next time one does.
- Recover from a fault with a re-home, after re-proving all three drivers.
- Make the final ACK of an interrupted move say why it was interrupted, and
  make the final ACK of `FIXED_XYZ` report the first axis that was refused.
- Take EN off in a fatal error handler for the pellet image, before halting as
  Zephyr's default handler does.
- Make a stopped motor able to move again. The new stop path stops the DMA and
  the stepper's timer counter and drops every queued block, so the next move
  starts from an empty queue and a stopped counter.
- Fix two bugs in `motor_motion.c` and `motor_motion_workq.c` that nothing
  called before, and that the new stop paths now reach. `motors_all_stop`
  passed a stepper device to `servo_motor_stop`. `set_all_e_stop_flags` set the
  stepper flags a second time instead of the servo ones.
- Set the pellet main thread's stack to 1536 bytes (`CONFIG_MAIN_STACK_SIZE`,
  not set before), because the re-proof path was estimated from the code to
  leave only 32 to 88 bytes of margin, and an overflow halts the board.
- Add the `ll,stepper-power` devicetree binding and a `stepper_power` node on
  the pellet board. The feature compiles only where such a node exists, so the
  magnet and IO module images do not build any of it.
- Add two `motor_math` shell commands, described under "Shell".

## Wire protocol

No new frame and no layout change. `JERRYCAN_WIRE_SCHEMA_VERSION` stays `1`.

`JERRYCAN_CMD_STEPPER_STATUS = 0x16`, board to host, 12 bytes, unchanged:
`motor_id`, `status`, `homing_status`, `limit_switch`, `position`,
`send_position`. One frame per stepper every 100 ms. Only `status` changes
meaning:

| Bit | Name | Meaning |
| --- | --- | --- |
| `1 << 0` | `DRIVER_FAULT` | This motor's driver raised DIAG; latched until a re-home |
| `1 << 1` | `ENABLE_OFF` | The shared enable is off, for any reason |

The value for each motor is the first row that matches:

| Condition | `status` of the motor |
| --- | --- |
| No enable net (v1.2) | `0x00` |
| ESTOP asserted | `0x02` |
| Drivers not proven configured | `0x02` |
| A fault is latched | `0x03` for each driver that faulted, `0x02` for the others |
| Host silent | `0x02` |
| Otherwise | `0x00` |

`ENABLE_OFF` alone does not say why EN is off. The ACK error does (below). A
failed driver proof sets `ENABLE_OFF` and not `DRIVER_FAULT`. "Not proven" ranks
above a latched fault, so after a re-home whose proof fails, the `DRIVER_FAULT`
bit goes away while moves keep being refused with `-EIO`.

`JERRYCAN_CMD_ESTOP = 0x00`, host to board, 1 byte. The arbitration id is the
board address, or `0x01F` to broadcast:

| Field | Type | Meaning |
| --- | --- | --- |
| `rsvd` | `uint8` | Non-zero asserts ESTOP, zero releases it |

The field is named `rsvd` in `jerrycan_types.h`; this firmware reads it as the
assert flag. ESTOP is one-shot and draws no ACK.

## Capability bits

| Bit | Name | Set by this firmware |
| --- | --- | --- |
| `1 << 0` | `TIMING_TRAILER` | No |
| `1 << 1` | `TIME_SYNC` | No |
| `1 << 2` | `FINITE_GPIO_PULSE` | Yes, where the board has a pulse counter |
| `1 << 3` | `PELLET_PRECHECK` | No |
| `1 << 4`, `1 << 5` | | Taken on `feat/pellet-board-timing` and `feat/io-module-firmware`; not defined here |
| `1 << 6` | `STEPPER_DRIVER_FAULT` | Yes, on a board that found its enable net at boot |

The new bit is `1 << 6` and not `1 << 4` because the timing and IO lines
already use bits 4 and 5.

A pellet v1.2 answers `0x00000004`. A pellet v1.3 answers `0x00000044`.

Bit 6 means the board found the enable net at boot and will report the status
bits above. It does not mean the drivers were proven, and it does not mean EN is
on. It rests on a single sample of PD2, so a v1.3 board that sampled low would
leave bit 6 clear and behave as a v1.2 board: moves accepted, motors disabled.
The boot log line `Capabilities 0x...` does not show bit 6, because the bit is
added per request. Read it from the `CAPABILITIES_RESPONSE`.

## ACK errors

The `error` field of `JERRYCAN_RSP_ACK` is the firmware's errno, as a negative
number. Zephyr's minimal libc defines these values, and they are not all
Linux's. `ETIMEDOUT` is 116 here and 110 on Linux, so a host must compare
against the number and not against its own `errno.ETIMEDOUT`.

| Value | Name | Meaning on the pellet |
| --- | --- | --- |
| `-1` | `EPERM` | ESTOP is asserted. Stepper moves, homes and servo moves are refused. A move that ESTOP interrupted ends with it |
| `-5` | `EIO` | A driver fault is latched, or the drivers were not proven configured. Refused until a re-home succeeds (fault) or the board reboots (not proven) |
| `-16` | `EBUSY` | The axis is already moving, or the axis needs homing |
| `-116` | `ETIMEDOUT` | EN is off because the host went silent |

A refused `STEPPER_MOVE` or `STEPPER_HOME` is ACKed at once with the error. A
move that was already running when it was stopped gets its ACK on the next
status tick (100 ms), carrying the board-wide error at that moment. The error is
board-wide, so a move that finished normally just before a fault or an ESTOP,
inside the same tick, can also ACK with it. A command frame that arrives after
the board went silent is not refused with `-ETIMEDOUT`: the frame ends the
silence before its handler runs. So `-ETIMEDOUT` reaches a host only as the
final ACK of a move the silence cut off, or of a `FIXED_XYZ` that was still
working through its axes.

`FIXED_XYZ` has one ACK for three axes. It reports the first axis that was
refused: `-EPERM`, `-EIO`, `-ETIMEDOUT`, or `-EBUSY` when that axis was not
already moving. An axis already at its target (`-EAGAIN`) does not count. If no
axis was refused, it reports the board-wide error at that moment, which is 0
when nothing is wrong.

## ESTOP

- Asserting stops every moving stepper and servo, stops the DMA and the timer
  counter and drops the queued blocks, marks every axis as needing a home, and
  takes EN off (v1.3).
- It stays asserted until a frame with payload 0 arrives. It is held in RAM,
  so a reboot also releases it.
- While asserted, stepper moves, homes and servo moves are refused with
  `-EPERM`. A v1.3 board reports `ENABLE_OFF` for every motor.
- On release, EN returns if nothing else holds it off: the drivers are proven,
  no fault is latched, and the host is not silent. Every axis still needs a
  home, so a move is refused with `-EBUSY` until that axis has been homed.
- The `estop_active` bit in `JERRYCAN_CMD_STATUS` (`0x01`) stays 0. ESTOP shows
  only in the stepper status and in ACK errors.
- On a v1.2 board ESTOP still stops motion and refuses moves with `-EPERM`;
  there is no EN to drop and the status bits stay 0. No host sends ESTOP today.

## Host silence

- The timeout is 30 s (`CONFIG_LIB_MOTOR_MOTION_HOST_SILENCE_TIMEOUT_MS`,
  range 5000 to 600000; the pellet does not override the default).
- Any received frame counts if the low five bits of its arbitration id equal the
  board's address or `0x1F`. The test comes before the command type is read, so
  `HEARTBEAT`, `CAPABILITIES_REQUEST`, `CFG_READ` and a type the board does not
  know all count. The shell commands `motor_math stepper_move` and
  `stepper_home` count too.
- The 30 s starts when the drivers are proven at boot. The poll runs every
  100 ms, so EN goes off up to about 100 ms after the 30 s mark.
- On silence the board takes EN off, stops any stepper that was moving and
  marks only those steppers as needing a home. Servos are not touched. Status
  is `ENABLE_OFF` for every motor.
- The next frame addressed to the board puts EN back on, with a 1 ms settle,
  before its command runs. The datasheet (rev 1.09) states no delay from ENN
  low to the first step, so the 1 ms is a margin.
- A host that is alive but quiet cannot be told from a dead one. A `HEARTBEAT`
  every few seconds keeps EN on.

## Faults and recovery

DIAG is the OR of stall detection, driver power-on reset, charge-pump
undervoltage, overtemperature, and a latch set by shorts and overtemperature
(datasheet rev 1.09, Figure 15.1). ENN high resets only that latch. The
firmware keeps StallGuard off (`SGTHRS = 0`, `TCOOLTHRS` unwritten), so stall
detection does not fire. A fault can therefore also mean that a driver reset
or that the supply dipped, not only a short or overheating.

- A reading counts only while EN is on, and only if it is high on two
  consecutive 100 ms polls. A DIAG that stays high after EN goes off, from an
  undervoltage or an overtemperature still present, shows again once EN
  returns.
- On a latched fault the board stops the steppers, reads DRV_STATUS and GSTAT of
  each faulted driver and logs the flags set, marks all axes as needing a
  home, and takes EN off last. The cause goes to the console log only. It is
  not on the wire.
- Moves are refused with `-EIO`. The faulted driver's motor reports `0x03`
  and the others `0x02`.
- A `STEPPER_HOME` for any axis recovers. Before EN returns, the board
  re-proves all three drivers: `IFCNT` must advance by exactly one when
  `IHOLD_IRUN` is rewritten with init's values, `GCONF` `pdn_disable` and
  `mstep_reg_select` must still be set, and `GSTAT` `reset` must be clear. By
  count that is 15 register accesses at 10 ms each, about 150 ms added to the
  home; it has not been timed.
- If all three pass, the fault latch clears for all three drivers and EN
  returns. Only the homed axis is homed. The others are still refused with
  `-EBUSY` until each is homed.
- If any driver fails, motion is refused with `-EIO` until a reboot. A further
  home repeats the check and is refused again. If DIAG is still high after a
  successful re-home, it latches again two polls after EN returns.
- Boot runs the same proof before EN first goes on. A driver that fails it
  leaves EN off and motion refused with `-EIO` until a reboot.

## Fatal errors

A fatal error on the pellet (a CPU exception, a stack overflow, `k_oops()`,
`k_panic()`, an unhandled interrupt) now runs a handler that takes EN off with
one GPIO write, then halts exactly as Zephyr's does. With interrupts locked the
DMA completion that stops a stepper's timer cannot run, so STEP likely keeps
pulsing after a halt; that is reasoned from the code and not measured. With EN
off the motors stop. A reset is deliberately not used, because it would change
v1.2 behavior. The handler is in the pellet image only, and the magnet and IO
images keep Zephyr's default. It has never run: `fault_safety.c` is
compile-checked only.

## Shell

- `motor_math stepper_power_status` prints `detected`, `ready`, `fault mask`,
  `silent`, `estop`, `enable` and `diag`, then runs the driver proof on each
  driver and prints its result. The proof is UART traffic, and on a v1.2 board
  this typed command is the only thing that causes any.
- `motor_math stepper_power_oops` triggers a fatal error on purpose, to show
  that EN goes off. It halts the board on either hardware revision, until it is
  reset.

## Behavior on a v1.2 board

With no enable net detected the module logs `no stepper enable net`, sets PD2
to disconnected, and from then on touches no pin and adds no UART traffic. It
does not configure the DIAG pins, install the frame hook, or schedule the poll.
Capability bit 6 is clear and every `status` byte is 0, as before. None of the
new refusals can occur there unless an ESTOP is sent, so `FIXED_XYZ` and single
moves ACK as in v2.3.0.

What a v1.2 board does carry from this change:

- the ESTOP handler, and the new stop path that only it reaches there;
- the pellet fatal error handler, which touches no pin there;
- the 1536 byte main stack;
- the two `motor_math` shell commands.

## Known limitations

1. A single move interrupted and released within one 100 ms status tick may
   ACK 0, because the error is sampled at the tick and not at the stop. It
   takes an ESTOP pulse shorter than the tick.
2. `-EBUSY` means either "axis already moving" or "axis needs homing". Host
   code cannot tell them apart from the number alone. `homing_status` in the
   status frame is the current move type, not whether a home is owed.
3. The `DRIVER_FAULT` status bit is hidden while ESTOP is asserted. It
   reappears on release. `ENABLE_OFF` still shows.
4. A move stopped by a limit switch keeps two behaviors from v2.3.0, left
   unchanged so that v1.2 stays as it is. A block left in the queue can leave
   the axis stuck at `-EBUSY` until a reset. The timer also keeps running, so
   the next move may emit a few unplanned step pulses while its table is
   computed. The shell `stepper_stop` takes the same route. Neither has been
   measured on hardware. The ESTOP, fault and silence stops do not have this
   problem, because they drop the queue and stop the counter.
5. Homing has no timeout. With a dead limit switch and a live host, the motor
   runs until someone stops it. Host silence only covers a dead host.
6. A driver reset shorter than two 100 ms polls goes unnoticed. It leaves that
   driver at its power-up defaults (`IRUN = 31`) with EN on, and nothing
   notices until a fault latches and a re-home re-proves it. The shared 12 V
   rail should make a short dip unlikely, but this has not been measured.
7. The magnet image has not linked since v2.3.0. `z_impl_sys_rand_get` is
   undefined, because `capabilities.c` needs an entropy driver that the magnet
   `prj.conf` does not enable. It is unrelated to this change and out of scope
   here. The magnet image can only be compile-checked.

Also found by reading the code, not measured:

- A silence stop marks only the steppers that were moving as needing a home.
  An axis that was idle when EN went off stays marked as homed with its motor
  unpowered. If the load can move it with EN off, its position is stale and
  nothing says so.
- An ESTOP frame that arrives while the board is silent puts EN on for about
  1 ms (the settle) before the handler takes it off again. Nothing steps in
  that time.

## Not changed

- No watchdog runs on the pellet. `&iwdg` is enabled in the devicetree and
  nothing feeds or starts it, so a hang that is not a fatal error leaves EN as
  it was.
- The fault cause is on the console log only, not on the wire.
- StallGuard stays off, and EN stays shared and board-wide. There is no per-move
  enable.

## Acceptance criteria

None of these has been checked. Each is a thing to see on a board before the
release is tagged.

On a v1.2 board, where nothing should change:

- The firmware version request reports `2.3.1` after reboot and finalization.
- The boot log shows `no stepper enable net`.
- `capabilities = 0x00000004`, with bit 6 clear.
- The `status` byte of every stepper status frame is 0, idle and moving.
- Home, move and `FIXED_XYZ` ACK 0 as on v2.3.0.

On a v1.3 board:

- `capabilities = 0x00000044`, and `boot_id` does not change across requests
  within one boot.
- With a frame reaching the board at least every few seconds, the `status` byte
  of all three motors is 0 and the motors move on command.
- After 30 s with no frame addressed to the board, the `status` byte of all
  three motors is `0x02`. The next frame brings it back to 0, and a move works.
- ESTOP asserted during a move: that move's ACK is `-1`, once. A move sent
  while asserted is refused with `-1`. After release, a move is refused with
  `-16` until the axis is homed, and then works.
- DIAG forced high on one driver: the move in progress ends with ACK `-5`; that
  motor's `status` is `0x03` and the others' `0x02`; a further move is refused
  with `-5`; a home clears all of it.
- `motor_math stepper_power_oops` takes EN low before the board halts.

## How to verify on a rig

Capabilities, as for v2.3.0. The request is arbitration id `0x460` and the
response is `0x480`:

```bash
candump -T 30000 'can0,480:7FF' > /tmp/caps.log &
# ask the board for its capabilities, then reboot it and ask again
```

The response is nine payload bytes. Expected, with the last four the boot id:

```text
v1.2:  01 04 00 00 00 xx xx xx xx
v1.3:  01 44 00 00 00 xx xx xx xx
```

The stepper status frames are on `0x2C0` for address 0 (`0x16 << 5`). Byte 1 of
the payload is `status`.

The rest is `firmware/lib/motor_motion/test/hil_stepper_power_check.py`, which
covers the capability, status, ESTOP, fault and silence items above. It does
not cover the version request or the fatal error handler. **It moves the
motors.** Close reachAQ first, and keep the stage clear. Its ESTOP goes to the
broadcast address, so every module on the bus stops, not only the pellet.

```bash
python3 firmware/lib/motor_motion/test/hil_stepper_power_check.py --board v1.2 --channel can0 --address 0
python3 firmware/lib/motor_motion/test/hil_stepper_power_check.py --board v1.3 --channel can0 --address 0
```

It prints PASS, FAIL or SKIP for each check, and never PASS for a check it
could not run. `diag_fault` needs `--axis N` and an operator to force DIAG.
`silence_cycles` takes about 21 minutes. `silence_midmove` needs an image built
with `-DCONFIG_LIB_MOTOR_MOTION_HOST_SILENCE_TIMEOUT_MS=5000` and
`--silence-timeout-s 5`. The script has not been run against a CAN interface
yet. A serial console shows the state with `motor_math stepper_power_status`.

## Host work

None of this is done by this change. Today's reachAQ keeps working without
it, apart from the allowlist entry.

- **Required to run it.** Add `2.3.1` to
  `config/pellet-firmware-compatibility.yaml`, and run `reachaq-sync` on each
  rig before flashing. reachAQ refuses a firmware version it does not list, and
  the updater will not flash one.
- **To use the reports.** Add `stepper_driver_fault: 1 << 6` to
  `CAPABILITY_BITS` in `tools/acquisition/model/firmware_compatibility.py`, and
  read `stepper_status.status` in `_translate_stepper_status()` in
  `auto-trainer-device/src/autotrainer/device/can_interface.py`. Today a fault
  appears to reachAQ only as an ACK error.
- **To recover.** reachAQ must re-home after a fault, and treat `-EBUSY` as
  "needs homing". The compound `home` already exists.
- **To guard old firmware.** The flash path could refuse an image below 2.3.1
  when the running board reports bit 6. A revert on a v1.3 board lands on
  whatever the other MCUboot slot holds, and if that is older than 2.3.1 the
  motors stay disabled. The v2.3.0 deployment flashed twice so both slots carry
  the release.
- **If reachAQ adds `HEARTBEAT`** (the IO module needs it anyway). It counts as
  host traffic automatically, and keeps EN on while the host is alive.
