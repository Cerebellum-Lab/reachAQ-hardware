## Changes

- Append a 20-byte timing trailer to every frame whose payload leaves room for
  one. It says when the thing the frame describes happened on the board's
  clock, which boot that clock belongs to, and the frame's place in the
  board's sequence.
- Answer `JERRYCAN_CMD_TIME_SYNC_REQUEST` (`0x1F`) with
  `JERRYCAN_CMD_TIME_SYNC_RESPONSE` (`0x20`): reachAQ's NTP-style exchange,
  stamped in the CAN receive interrupt.
- Listen for the timekeeper's `JERRYCAN_CMD_SYNC_CLAP` (`0x25`) from any
  address and report each one heard with `JERRYCAN_CMD_SYNC_CLAP_OBSERVED`
  (`0x26`).
- Stamp each frame with the time its contents refer to, where the board knows
  it:
  - a pressure frame at its ADC sample (`SAMPLED`; `TX_QUEUE` until the first
    sample);
  - a finite pulse at its physical start and end (`PHYSICAL_START`,
    `COMPLETED`);
  - a GPIO read at the read (`SAMPLED`);
  - a tone's reply to its play command at playback start (`PHYSICAL_START`,
    the marker edge itself only at 5 and 6 kHz).

  Periodic tone frames and door frames are `SAMPLED` when the frame is built,
  not when the door or tone changed. Every other frame, such as ACKs, stepper
  and servo status, and the LED, is `TX_QUEUE`.
- Keep board time on the Cortex-M4 DWT cycle counter, extended to 64 bits. The
  kernel's cycle count was rejected because it loses time. See Board clock.
- Report capabilities `0x00000017` on a v1.2 board
  (`timing_trailer | time_sync | finite_stim3_pulse | sync_listener`), and
  `0x00000057` on a v1.3 board, which adds bit 6, `stepper_driver_fault`.

## Wire protocol

### Timing trailer

The trailer is 20 bytes, appended after the uuid byte and read little endian
as `<BBBBIIQ`. A frame whose payload leaves fewer than 20 bytes free carries
no trailer. reachAQ already decodes it, in
`auto-trainer-device/src/autotrainer/device/socketcan_jerrycan.py`.

| Offset | Field | Type | Meaning |
| --- | --- | --- | --- |
| 0 | `tag` | `uint8` | `0xA7` |
| 1 | `version` | `uint8` | `1` |
| 2 | `kind` | `uint8` | What `board_time_us` marks, below |
| 3 | `flags` | `uint8` | Bit 0 `COALESCED`: a rate cap merged events, and the time is the latest of them |
| 4 | `boot_id` | `uint32` | The same boot id as `CAPABILITIES_RESPONSE` |
| 8 | `sequence` | `uint32` | Counts this board's trailer-bearing frames. A frame dropped from a full transmit queue also advances it, so a gap means a lost frame |
| 12 | `board_time_us` | `uint64` | Board time in microseconds |

| `kind` | Name | Marks |
| --- | --- | --- |
| 0 | `TX_QUEUE` | When the frame was queued for sending |
| 1 | `OBSERVED` | When the board saw an external event, such as a clap |
| 2 | `COMMAND_RECEIVED` | When the command this frame answers arrived |
| 3 | `PHYSICAL_START` | When an output physically started |
| 4 | `COMPLETED` | When an output physically finished |
| 5 | `SAMPLED` | When the reported value was sampled |

### Time sync

`JERRYCAN_CMD_TIME_SYNC_REQUEST = 0x1F`, host to board, 12 bytes:

| Field | Type | Meaning |
| --- | --- | --- |
| `request_id` | `uint32` | Echoed in the response |
| `host_send_perf_ns` | `uint64` | The host's send time; the board does not use it |

`JERRYCAN_CMD_TIME_SYNC_RESPONSE = 0x20`, board to host, 20 bytes:

| Field | Type | Meaning |
| --- | --- | --- |
| `request_id` | `uint32` | From the request |
| `request_receive_time_us` | `uint64` | Board time the request arrived, stamped in the CAN receive interrupt |
| `response_queue_time_us` | `uint64` | Board time this response was queued |

The response's trailer is `TX_QUEUE` at `response_queue_time_us` and carries
the `boot_id`. reachAQ ignores a response without one.

### Sync clap

`JERRYCAN_CMD_SYNC_CLAP = 0x25`, timekeeper to all, 4 bytes: `tick`
(`uint32`). Accepted from any address.

`JERRYCAN_CMD_SYNC_CLAP_OBSERVED = 0x26`, board to host, 5 bytes: `tick`
(`uint32`) and `clapper_node` (`uint8`), the clapping board's address. The
trailer is `OBSERVED` at the clap's arrival, stamped in the receive interrupt.
A pellet board sends it only when a timekeeper claps, so it is silent on
today's rigs.

Neither request is acknowledged. The time-sync response is the answer, and a
clap is a broadcast that nobody waits on.

## Capability bits

| Bit | Name | Set by this firmware |
| --- | --- | --- |
| `1 << 0` | `TIMING_TRAILER` | Yes |
| `1 << 1` | `TIME_SYNC` | Yes |
| `1 << 2` | `FINITE_GPIO_PULSE` | Yes, where the board has a pulse counter |
| `1 << 3` | `PELLET_PRECHECK` | No |
| `1 << 4` | `SYNC_LISTENER` | Yes |
| `1 << 5` | `TIMEKEEPER` | No; that is the IO module |
| `1 << 6` | `STEPPER_DRIVER_FAULT` | Yes, on a board that found its enable net at boot (v1.3) |

The three timing bits follow `CONFIG_LIB_JERRYCAN_TIMING`, the same switch
that compiles the trailer, the responder and the clap listener, so a board
reports them exactly when it has them.

A pellet v1.2 answers `0x00000017` and a pellet v1.3 `0x00000057`. Bit 6 is
added per request, as in v2.3.1, so the boot log line `Capabilities 0x...`
prints `0x17` on both: read the value from the response. What bit 6 means, and
what it does not, is in v2.3.1's "Capability bits".

## Board clock

Board time is the DWT cycle counter, extended to 64 bits in software, at
170 MHz. A keep-alive reads it at least every 10 s, so a 32-bit wrap
(25.26 s) is never missed. It also re-enables the counter if a debugger
cleared it, and logs one warning when it does. Cycles that pass while a
debugger has the counter disabled are not recovered, so board time steps after
a debug-probe detach.

The kernel's cycle count was not usable: Zephyr 3.7's tickless SysTick loses
cycles every time it is reprogrammed, so a clock built on it runs slow by an
amount that depends on the workload. The bench run below is consistent with
that, as evidence rather than a verdict. In DWT time on the same crystal, the
100 ms kernel timer behind `GPIO_READ` ran 45.3 ppm long idle and 54.3 ppm long
under load, one run of each. Over the same phases the DWT clock's rate against
the host changed by 0.086 ppm. That this is the SysTick reprogram loss is
likely, not shown.

Board time starts at an arbitrary point within the first 25.3 s of a reset; it
is not the uptime. A host fits it separately for each `boot_id`.

## Host silence

On a v1.3 board the stepper enable (EN) goes off when no host frame has
arrived for 30 s, and the next host frame puts it back. That is v2.3.1's rule,
and its "Host silence" section has the details: the timeout
(`CONFIG_LIB_MOTOR_MOTION_HOST_SILENCE_TIMEOUT_MS`, 30000 on the pellet), the
100 ms poll, what the board stops and marks as needing a home, and the 1 ms
settle. A v1.2 board has no enable net, installs no hook and has no timeout.

One thing changes in this image: **a frame counts only if it comes from the
host.** `SYNC_CLAP` never counts, whatever its address.

- A frame counts if the low five bits of its arbitration id equal the board's
  address or `0x1F`, and it is not a board frame. For a host frame those bits
  are the destination, so `HEARTBEAT`, `CAPABILITIES_REQUEST`, `CFG_READ`,
  `TIME_SYNC_REQUEST` and a type the board does not know all count.
- A clap is a board frame. The clap listener takes it from any address, `0x1F`
  and the board's own included. For a board frame the low five bits are the
  sender, not the destination, so the address test alone would take a clap
  from those two addresses for a host command, and it would keep EN on
  indefinitely. The timekeeper, at address 8, never could.
- The test is `is_board_frame_type()` in `jerrycan.c`. Every message type that
  an RX filter admits from any address must be listed there. Today that is
  `SYNC_CLAP` only.
- This is not shown on a board yet. The clap-only run under "How to verify on a
  rig" is what shows it.
- A `TIME_SYNC_REQUEST` that ends a silence puts EN back first, and the 1 ms
  settle makes that response show about 1 ms more board turnaround. The
  response carries both the receive time and the queue time, so the host's fit
  is not biased, but a filter on round-trip time may drop that one sample.

## What did not change

By design, the timing change leaves these as v2.3.1 has them, and the pellet
regression qualification after tagging checks it: pins, CAN IDs, the payload
bytes ahead of the trailer, rates, behavior, and wire schema `1`. The magnet
module's wire format is unchanged.

Kernel timers still run on SysTick, as in v2.3.0, so periodic frames keep their
v2.3.0 timing. On this build the 100 ms `GPIO_READ` period measured 45 to 54 ppm
long. v2.3.0 was not measured, and nor was the 12 ms pressure timer. Where a
frame carries a physical time, that time says when the event happened. Other
frames say when they were queued.

## Compatibility

v2.4.0 is **not** safe on current reachAQ. It advertises `time_sync`, so
reachAQ's `open()` runs 4 back-to-back time syncs, and current reachAQ's
board-clock fit raises on those closely spaced, noisy observations and
aborts. Current reachAQ cannot open a v2.4.0 board. reachAQ v3.0.0's tag
records the same.

reachAQ's board-clock robustness fix, branch `feat/io-timing-clock-chain`
(T3), must ship first. Until it has, the allowlist entry below is not added
and v2.4.0 is not tagged or deployed. The release flasher also refuses a
version the rig's reachAQ does not list. The bench run needed
`--allow-unqualified`.

The storage-partition fix
([#3](https://github.com/Cerebellum-Lab/reachAQ-hardware/pull/3)) is in this
build, as it is in v2.3.1. The first update to the fixed layout loses the
stored settings once, because the store moves to a new address. After that they
persist across reboots and updates; that rests on #3's tests and has not been
shown with this image. After that first update, rewrite the configuration of
all five motors: the steppers `x`, `y` and `z`, and the servos `load` (servo 1)
and `cover` (servo 0). Then re-save the `FIXED_XYZ` positions and home each
axis. reachAQ rewrites the motor configuration when it initializes the
hardware, but not after a reboot mid-session.

## Limits

- Board time is per boot. Times from two boots cannot be compared without the
  host's fit for each.
- A frame with fewer than 20 bytes free carries no timing.
- The pellet never sets `COALESCED` and never sends `COMMAND_RECEIVED`. Both are
  defined for other boards.
- Board time steps after a debug-probe detach. See Board clock.
- An address clash is not detected. A non-clap frame from another board
  configured at the pellet's own address counts as host traffic, because the
  CAN id cannot tell it from a host frame: its low five bits are that address.
  A correctly addressed bus never produces one. This is a known limit and is
  not fixed.

## Acceptance criteria

- Firmware version request reports `2.4.0` after reboot and finalization.
- `CAPABILITIES_RESPONSE` carries `wire_schema_version = 1` and
  `capabilities = 0x00000017` on a v1.2 board, `0x00000057` on a v1.3 board.
- Every `TIME_SYNC_REQUEST` draws a response whose trailer is `TX_QUEUE` at
  `response_queue_time_us` and carries the capabilities' `boot_id`.
- Periodic frames carry trailers with no sequence gaps, and a tone reports
  `PHYSICAL_START`.
- v1.3: the clap-only `silence_cycles` run under "How to verify on a rig"
  shows `ENABLE_OFF` in every cycle with the sender at `0x1F` and at the
  pellet's own address, every clap answered, and the heartbeat control fails
  its first cycle.
- reachAQ with T3 opens the board and keeps aligning board times past 60 s.
- `qualify_pellet_firmware.py --expect-version 2.4.0` passes on the tagged
  bundle.

## How to verify on a rig

The check transmits on `can0`. Run it only with the rig lock held and nothing
else driving the board:

```bash
python3 firmware/lib/jerrycan/test/hil_timing_check.py --channel can0 --address 0 --play-tone
```

Add `--soak` for the clock soak, or `--rtt-report` for the round-trip report.
Each of those runs instead of the standard checks.

### Clap-only silence run (v1.3 board)

This shows that a clap does not reset the host-silence timer, which the merge
had to get right (see "Host silence"). It **moves the motors**
(`silence_cycles`): close reachAQ and keep the stage clear. It replaces the
clap check in v2.3.1's Merge-forward notes, which sends from address 8, the
default of `hil_timing_check.py --clapper-address`. A clap from 8 fails the
address test whether or not the type test exists, so that run passes on the
unfixed code too, and it never checked that the pellet received a clap.
`hil_timing_check.py` also refuses to clap from the pellet's own address.

Conditions:

- The image is the merged one in its release configuration, with the 30 s
  silence timeout. A build with `CONFIG_LIB_MOTOR_MOTION_HOST_SILENCE_TIMEOUT_MS`
  at 5000 is for iteration only (then pass `--quiet-s 7`); the record is a 30 s
  run.
- Nothing else may address the pellet while a quiet window runs: reachAQ closed,
  no updater, and no `hil_timing_check.py`, which sends `TIME_SYNC_REQUEST` and
  `CAPABILITIES_REQUEST`. Both are host frames. The preflight of
  `hil_stepper_power_check.py` refuses to start when it sees a host-only type
  that it knows, but it cannot see them all; do not rely on it.
- Hold the rig lock (`/tmp/reachaq-rig-exclusive.lock`) for the whole run.

`hil_clap_sender.py` sends only the one frame you choose, as FD frames with BRS,
and counts the pellet's answers. Each clap draws a `SYNC_CLAP_OBSERVED` (`0x26`)
whose `clapper_node` is the address the clap came from, which proves the pellet
received and dispatched it. The sender exits non-zero if it saw fewer than
sent minus one answers, or if any named another `clapper_node`.

Run it twice, once with the sender at `0x1F` (CAN id `0x4BF`) and once at the
pellet's own address (CAN id `0x4A0`, address 0 here). They reach the board
through different RX filters, and address 8 proves nothing. Start the sender
first and give it a `--duration` that outlasts the check. `silence_cycles` prints
its expected run time, about 17 minutes with the homes, so 1800 s is enough.
Then wait for the sender to print its result; an interrupted sender prints no
verdict. Use `--rate 10` for a stricter run.

```bash
# shell 1: claps from 0x1F, then again with --from 0 (the pellet's own address)
python3 firmware/lib/jerrycan/test/hil_clap_sender.py --channel can0 --address 0 --from 31 --rate 1 --duration 1800
# shell 2, once shell 1 is sending
python3 firmware/lib/motor_motion/test/hil_stepper_power_check.py --board v1.3 --channel can0 --address 0 --check silence_cycles
```

Pass, for each of the two runs:

- `silence_cycles` shows `ENABLE_OFF` on all three motors in every cycle, about
  30 s after the last frame the script sent (within about 100 ms of the poll),
  and ends with PASS.
- The board console logs `No host frame for 30000 ms: stepper enable off` once
  per cycle.
- The sender prints `[PASS] clap_receipt: sent N, observed N, mismatched 0` (one
  fewer observed is allowed for a reply still in flight).

Positive control. The same bench with `HEARTBEAT` (`0x3F`) to `0x1F` in place of
the claps, at the same rate. A heartbeat is a host frame, so `ENABLE_OFF` must
not appear: the first cycle fails with `motor 0 status 0x00, want 0x02`, and
`silence_cycles` stops there. That shows the bench can see a timer reset; a run
where the control also shows `ENABLE_OFF` proves nothing about claps. The sender
has to keep sending through the first quiet window, so give it a long
`--duration` and stop it (Ctrl-C) after the check has failed:

```bash
# shell 1
python3 firmware/lib/jerrycan/test/hil_clap_sender.py --channel can0 --address 0 --frame heartbeat --rate 1 --duration 600
# shell 2
python3 firmware/lib/motor_motion/test/hil_stepper_power_check.py --board v1.3 --channel can0 --address 0 --check silence_cycles --cycles 3
```

### Stack check

The interrupt stack (2048 bytes, `CONFIG_ISR_STACK_SIZE`) has not been measured
on this image. The stepper status timer in `stepper.c` runs `jerrycan_tx` in
interrupt context, beside the TIME_SYNC responder and the clap listener. The
image has `CONFIG_KERNEL_SHELL`, `CONFIG_INIT_STACKS` and `CONFIG_THREAD_NAME`,
so `kernel stacks` on the board's serial console prints the interrupt stack and
each thread with its size and unused bytes.

Read it with TIME_SYNC and claps loading the board together. Run the clap
sender at 10 Hz from address 8, the timekeeper's, while the clock soak runs.
The soak sends 5 TIME_SYNC requests per second for 335 s and then 200 per
second for 335 s. Type `kernel stacks` at the end of the load phase. Read it
again after a fault re-home (`hil_stepper_power_check.py --check diag_fault
--axis N`, which needs an operator to force DIAG). Record the interrupt stack
and each thread against its size.

```bash
# shell 1
python3 firmware/lib/jerrycan/test/hil_clap_sender.py --channel can0 --address 0 --from 8 --rate 10 --duration 800
# shell 2
python3 firmware/lib/jerrycan/test/hil_timing_check.py --channel can0 --address 0 --soak
```

## Allowlist entry for reachAQ

Add this to `config/pellet-firmware-compatibility.yaml` after rig
qualification. Do not add it before reachAQ's board-clock robustness fix (T3)
has shipped and the release is tagged.

```yaml
  - version: 2.4.0
    wire_schema_version: 1
    required_capabilities:
      - finite_stim3_pulse
      - timing_trailer
      - time_sync
    optional_capabilities:
      - sync_listener
      - stepper_driver_fault
    hardware_release: v2.4.0
    tested_reachaq_release: pre-release-devel
    qualification_status: rollout_pending
    qualification_date: null
```

`sync_listener` is optional because reachAQ consumes claps only after T3.
`stepper_driver_fault` is optional because only a v1.3 board reports it: a v1.2
board answers `0x17`. v2.3.1's Host work says reachAQ must define
`stepper_driver_fault: 1 << 6` in `CAPABILITY_BITS` in
`tools/acquisition/model/firmware_compatibility.py` to use the bit. Confirm it
is there before this entry names it.
